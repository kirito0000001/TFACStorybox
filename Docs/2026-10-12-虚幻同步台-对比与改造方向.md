## 0. 结论摘要

1. **剧情这边的管线其实不差**：它已经是「C# 只写清单和脚本，起**一次** `UnrealEditor-Cmd`，素材全由 Python 侧 `AssetImportTask` 导入」。所以慢的**不是**「每个文件起一次进程」，而是清单构建阶段的重复全量扫描、以及 Python 侧逐项 fsync 写进度。
2. **最该从零境学的是「在线 / 离线双路」**：编辑器开着时走远程执行（快约十倍、能读到离线读不到的资产），连不上才退回离线。剧情现在**只有离线一路**，而且检测到编辑器开着还会去**强关它**。
3. **第二该学的是「怎么判成败」**：零境一律看**结果文件是不是本轮写出来的**，不看退出码。
4. **零境的同步台 UI 是个反面教材**：整页约 1000 行直接写在 `MainWindow.xaml` 里，`Controls/` 一个都没用上。**不要照搬**。
5. **落点整体要换到新工程**：从旧的 `{Target}/{BackGround,BGM,Voice,Lustration}` 换成 `AssetMaterial/...` 结构，并且**从「写数据表」升级成「写蓝图/CDO 变量」**——这是本次最大的变化。

### 1.2 核心：在线 / 离线双路 ← 最该学的一件

全部收在一个方法里：`Services/UnrealPythonTaskExecutionService.cs:41`

```csharp

                                   remoteJobPath, offlineStartInfo,
                                   bool? useRunningEditor = null)
// → record UnrealPythonTaskLaunch(ProcessStartInfo StartInfo, bool UsesRunningEditor)
```

调用方只认这个 record。

**怎么判定编辑器在跑**（`ShouldUseRunningEditor`，同文件 `:114`）：

- `Process.GetProcessesByName("UnrealEditor")`
- **刻意不用 WMI**（避免引入 `System.Management`），改用「主模块路径 + 主窗口标题」拼描述串 `$"{modulePath}|{MainWindowTitle}"`（`:194`）
- 项目匹配：描述串含 `.uproject` 绝对路径，**或**标题分词后含项目名
- `:108-113` 记录旧 bug：只判进程名时，开着别的工程也走在线路，然后在连接阶段整个失败

| | 在线（编辑器开着） | 离线（编辑器没开） |
|---|---|---|
| 启动 | 引擎自带的 `.../Python3/Win64/python.exe` 跑 `run_remote_unreal_job.py --job <job.json>` | `UnrealEditor-Cmd.exe <uproject> -run=pythonscript ...` |
| 实际执行 | Unreal **Python 远程执行协议**，脚本在**已在运行的编辑器里**跑 | 冷启一个无头编辑器 |
| 耗时 | 「快约十倍」 | 冷启动十几到 40 秒 |

**回退规则**（`MainWindow.UnrealSync.Shared.cs:52-81`）：只有连不上编辑器（标记 `ZD_REMOTE_UNAVAILABLE`）才回退；脚本自己失败**不**回退。回退时写 warning + 弹提示条。

**能力差异（只有在线能做）**：① 在编辑器里定位资产；② 读 `WidgetBlueprint` / `MetaSoundSource`（实测**在线 23 项 0 错、离线 4 项全报未找到**）→ 为此专门加了 `Unavailable` 档：不算错误、不挂到第一步。

#### 2.5.3 ⚠️ 三处不一致，需要你定

**不一致 #1：新工程的 MusicActor 没有 `SceneIndex`。**

你口述的「环境音 → 置入 `DisplayName="环境音频索引" int SceneIndex = -1;`」是 **CrossingVoid 那份**（`C:\CrossingVoid\Plugins\CrossMainData\...\MusicPlayerC.h:81-82`）的定义。

**MyWhiteHairedKiller 用的 `GALLibrary` 那份没有 `SceneIndex`。** 两份逐行比过，差异只有 4 项（其余完全相同）：

| 成员 | CrossMainData | GALLibrary |
|---|---|---|
| `FString BGMName`（BGM名称） | ✅ | ❌ |
| `int SceneIndex = -1`（环境音频索引） | ✅ | ❌ |
| `bool InitBGMaps(...)`（初始化BGM列表） | ✅ | ❌ |
| `void PlayBGM(...)`（播放指定BGM） | ✅ | ❌ |

**已核实：WHK 的 `MusicPlayer.uasset` 是一个蓝图**（`BlueprintGeneratedClass`），父类写死为 **`/Script/GALLibrary.MusicPlayerC`**（文件里该引用出现 6 次，`CrossMainData` 出现 **0** 次）。

→ 所以「把 CrossMainData 那份 `MusicPlayerC` 复制到 WHK」有个副作用：**两边类名都叫 `AMusicPlayerC`、`DisplayName` 都是「MusicActor」、还都定义了 `FTableVoices`**，会出现重名 UCLASS/USTRUCT；而且 WHK 现在这个蓝图**不会自动改挂到新类上**，得手工 Reparent。

**更省事的路子：不复制类，只给 `GALLibrary` 的 `AMusicPlayerC` 补成员**（至少 `SceneIndex`，需要的话再补 `BGMName` / `InitBGMaps` / `PlayBGM`）——一行 UPROPERTY，两个项目的 MusicActor 就对齐了，不引入重名、不用 Reparent、不用动蓝图。

**→ 结论：写 `SceneMaps`（列表），不写 `SceneIndex`。**

证据在 `MusicPlayerC.cpp` 里（两份都一样）：

```cpp
USoundWave* ReadyPlay = BGMaps[AudioIndex].LoadSynchronous();   // MusicPlayerC.cpp:52
```

`AudioIndex`（DisplayName「BGM音频索引」）是**运行时**用来索引 `BGMaps` 的游标，不是给人填的素材数据。
`SceneIndex` 与它完全对称（都是 `int = -1`、都紧挨着对应的 Map 列表），所以同样是运行时状态。
工具箱该写的是**列表**：`BGMaps` / `BGMapsLoopStart` / `SceneMaps` / `VoiceMaps`。

**顺带一个重要结论**：既然只写这 4 个列表，而它们**在 `GALLibrary` 的旧版里全都有**，
那「把 CrossMainData 的类复制过来」对本同步需求**并不是必需的**——但按「WHK 丢了、以零境为准」的思路，
把 WHK 推回新版仍然值得做：

| 路子 | 代价 | 说明 |
|---|---|---|
| **A. 不动类** | 0 | 只写 4 个列表的话，旧版够用 |
| **B. 用 CrossMainData 的内容替换 `GALLibrary` 的 `MusicPlayerC.h/.cpp`**（保留 `GALLIBRARY_API` 宏与文件路径） | 小 | 一次拿到新版全部成员；**类路径不变**，现有 `MusicPlayer.uasset` 蓝图不用 Reparent |

⚠️ **B 路千万别做成「新增第二个类」**：那会变成两个同名 `AMusicPlayerC` + 两个同名 `FTableVoices`，
而且现有蓝图的父类写死 `/Script/GALLibrary.MusicPlayerC`，**不会自动改挂**。
**替换同一模块里的那两个文件**才是安全的做法。可行性已确认：`MusicPlayerC.h` 只 include
`CoreMinimal.h` / `GameFramework/Actor.h`，`.cpp` 只多 `Components/AudioComponent.h` 和
`Kismet/KismetSystemLibrary.h`——**自包含，不依赖其它 CrossMainData 类型**。

**不一致 #2：`UI_Story.uasset` 的 `BGMaps` 是蓝图自建变量。**

`UI_Story` 是 WidgetBlueprint，全工程代码里搜不到同名 C++ 类，所以它的 `BGMaps` 是**蓝图里自己加的变量**。

这个区别很实际：
- **C++ UPROPERTY**（`MusicPlayer` 那些）→ Python 对 CDO `set_editor_property` + save 就行。**现在工具箱已经在对同一个资产做这件事**（写 `VoiceMaps`，S:801-874），所以有现成先例。
- **蓝图自建变量**（`UI_Story.BGMaps`）→ 只改 CDO 不够稳：蓝图下次编译会用 `FBPVariableDescription::DefaultValue` 重建生成类，把 CDO 上的改动盖掉。**要写 `FBPVariableDescription::DefaultValue`**。

**不一致 #3：ZDBridge 目前没有通用的「写蓝图变量」接口。**

`ZDBridgeFillBpVar.cpp` 确实在（`C:\CrossingVoid\Plugins\ZDBridge\Source\ZDBridge\Private\`），但它是**一次性硬编码**的工具：扫 `/Game/ITems/CharItemS` → 拼数组文本 → 写进 `GM_Main` 的 `Test_ALLcharGet` 函数图上的**局部变量** `ALLChar`，由命令行 `-ZDBpVarWrite` 触发。

手法是成熟的、可直接照抄：
1. 取 `FBPVariableDescription` 的 `DefaultValue`
2. `Modify()` → 赋值 → `MarkBlueprintAsStructurallyModified` → `CompileBlueprint`
3. **回读校验**（不一致就回滚、不保存）
4. `SavePackage`
5. **丢掉包重新加载**再比一次（并用「NSLOCTEXT 显示文本序列 + 条目数」比，因为引擎保存时会重生成 FText 的命名空间/键）

但它**不是可复用接口**：变量名、目标资产、函数图全写死在 `Run()` 里，而且写的是**局部变量**（`OwnerEntry->LocalVariables`），而 `UI_Story.BGMaps` 是**成员变量**（`Blueprint->NewVariables`）。

→ 要么**给 ZDBridge 加一个通用函数**（比如 `SetBlueprintVariableDefault(BlueprintPath, VariableName, ValueText)`），要么在工具箱的 Python 里用 `BlueprintEditorLibrary` 之类自己写。**我倾向给 ZDBridge 加通用函数**——回读+重载校验那套逻辑值得复用，别在 Python 里重写一遍。

ZDBridge 现有能力（`ZDBridgeLibrary.h`）：Paper2D/PaperZD 建资产、MetaSound 变量默认值、`UpsertDataTableRow` / `ApplyJsonToStructProperty` / `ReadDataTableRow`、`PurgeAssets`、`DetachSequencesFromAnimationSource`、灯光配置资产预加载、Niagara 特效那一套。**没有** 通用的"设蓝图变量默认值"。
