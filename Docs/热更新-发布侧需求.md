| # | 约束 | 后果 / 必须这么做 |
|---|---|---|

| 12 | 错误正文可能是 **HTML** 而不是 JSON（例：错 tag → 404 + 6832 字节 HTML 错误页） | 解析错误信息时不能假设 JSON |

## 3. 每个 Release 长什么样（契约）

### 3.1 Release 本体字段

| 字段 | 值 | 说明 |
|---|---|---|
| `tag_name` | `v{version}` | `version` 与清单里的 `version` **逐字相同**。例：`v1.0.1`、`v1.0.2-Beta`、`v1.0.2-Beta.2` |
| `name` | `TFAC剧情箱-轮椅版 v{version}` | 纯展示 |
| `body` | 更新公告正文 | 客户端在 `releaseNotes` 为空时用它兜底 |
| `prerelease` | **正式版 `false` / 测试版 `true`** | ★★★ 写错会把测试版推进**正式通道**，客户端会直接提示用户升级 |
| `target_commitish` | `main` | |

**判定规则**：版本号里**带了 `-` 后缀**（`-Beta` / `-Beta.2` / `-RC1` …）→ `prerelease = true`；否则 `false`。
判定必须**只看版本号字符串**，不要引入额外开关，避免"tag 说 stable、prerelease 说 beta"的自相矛盾。

### 3.2 附件（**名字必须逐字一致，ASCII**；分卷时不止三个）

> ★ **2026-10-06 增补（用户定案）**：整包超过 100 MiB 时会**自动按字节切卷**——此时上表第 1 行那个整包
> **不再作为附件上传**，改为上传 `…-win-x64.part01.zip`、`.part02.zip`…（拼接顺序即卷号顺序），
> `sha256.txt` 也从单行变成「整包 1 行 + 每卷 1 行」。完整契约见
> **`Docs\热更新-分卷与双通道-契约.md`**，与本节的旧描述冲突时**以它为准**。

| # | 附件名 | 内容 |
|---|---|---|
| 1 | `GalExcleTools-v{version}-win-x64.zip` | 更新包本体（**分卷时改为一组 `.partNN.zip`，不再上传整包**） |
| 2 | `GalExcleTools-v{version}-win-x64.sha256.txt` | **ASCII**：不分卷＝单行 `{64位小写sha256}  {zip文件名}`（sha256sum 风格，**两个空格**）+ 结尾换行；分卷＝第 1 行是整包、随后每卷一行 |
| 3 | `toolbox-update.json` | 更新清单（见 §4） |

⚠️ **`toolbox-update.json` 在每个 Release 里都叫这个名字** —— 客户端是在附件列表里**按名字**找它的。所以一个 Release 里**绝不能有两个同名附件**。

⚠️ 附件名里**不要有中文**（包名前缀是 ASCII 就是为了避开编码地狱）。zip **内部**的中文条目名没问题。

### 3.3 zip 内部结构（客户端 updater 直接依赖）

```
<zip 根>            ← 顶层就是程序目录本身，不要再套一层目录
├── TFAC剧情箱-轮椅版.exe          ← ★ entryExe，文件名含全角冒号 U+FF1A
├── TFAC剧情箱-轮椅版.dll
├── TFAC剧情箱-轮椅版.pri          ← ★ 文件名不能改（打包必需清单锁死了它）
├── App.xbf  MainWindow.xbf  Styles\ToolboxStyles.xbf
├── update-package.json            ← 包内体检单，打包时生成（§5）
├── Scripts\热更新覆盖.ps1          ← 更新器脚本，必须 UTF-8 with BOM
├── Scripts\update-whitelist.json   ← ★ 覆盖白名单，**必须进包**（理由见下面「打包禁忌」最后一条）
├── Tools\Atlas\python\…           ← 内置 Python 必须进包
└── Assets\…
```

**打包禁忌**：

- ❌ 不要把 `*.pdb` 打进包（`dotnet publish` 默认会带，要加 `-p:DebugType=None -p:DebugSymbols=false`）
- ❌ 不要把 `__pycache__\*.pyc` 打进包（运行时会被生成，属于垃圾）
- ❌ zip 根**不要**再多一层 `TFAC剧情箱-轮椅版\` 目录
- ⚠️ **`Scripts\update-whitelist.json` 要一起打进包**（客户端 2026-10-05 新增的要求）：`Scripts\` 整目录都在镜像白名单里，包里没有它 → 更新后安装目录里那份会被当成「包内已删」清掉。客户端为此做了兜底（它启动覆盖器前会把自己那份规则写进 `%LOCALAPPDATA%\GalExcleTools\UpdateRunners\update-whitelist.json`，覆盖器优先读那一份），所以**丢了也能更新**，但会让安装目录里的白名单缺席 —— 请照 §3 的目录树把它带上。

**分隔符与编码（实测，别踩）**：

- 条目名分隔符不统一：`Compress-Archive` / `.NET ZipFile` 写 `\`，**Bandizip 写 `/`** 且会写目录条目 → 发布侧**自己**比较条目名时先 `Replace('/', '\')` 归一化（客户端两种都能解）
- 中文条目名：三种打包器**都没写 UTF-8 flag（0x800）**，但 `.NET ZipFile.ExtractToDirectory` 与 `tar.exe` 解出来名字都正确 → **不需要**为此改打包方式
- 推荐压缩器：**Bandizip**（本机已装）`bz.exe c -fmt:zip -l:9 -r -y` —— 体积直接关系到 §2 的两道容量墙

## 4. 更新清单 `toolbox-update.json`（**逐字照抄这个结构**）

```jsonc
{
  "schemaVersion": 1,
  "toolboxStableKey": "GalExcleTools",
  "displayName": "TFAC剧情箱-轮椅版",
  "version": "1.0.1",
  "channel": "stable",
  "publishedAt": "2026-10-05T12:00:00+08:00",
  "releaseNotesUrl": "https://gitee.com/xiaojie578/TFACStorybox/releases/tag/v1.0.1",
  "releaseNotes": "本次更新内容……",
  "requiresManualMigration": false,
  "requiresRestart": true,
  "assets": [
    {
      "runtime": "win-x64",
      "fileName": "GalExcleTools-v1.0.1-win-x64.zip",
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
      "sizeBytes": 52428800,
      "downloadUrl": "",
      // ★ 2026-10-06 增补：只在分卷时出现；不分卷时**整个字段不存在**。
      //   顺序即拼接顺序；下面每一项描述的是**该卷自己**的哈希与大小，
      //   而上面的 fileName/sha256/sizeBytes 永远描述**拼接后的整包**。
      "parts": [
        { "fileName": "GalExcleTools-v1.0.1-win-x64.part01.zip", "sha256": "…", "sizeBytes": 31457280 }
      ]
    }
  ]
}
```

字段铁律：

| 字段 | 要求 |
|---|---|
| `toolboxStableKey` | 恒为 `"GalExcleTools"`（ASCII）。客户端会拿它跟自己的 key 比对，不等就拒绝 |
| `version` | 与 `tag_name` 去掉 `v` 之后**逐字相同**；语义化版本，beta 带 `-Beta` 后缀 |
| `channel` | `"stable"` 或 `"beta"`，**必须与 `prerelease` 一致** |
| `publishedAt` | ISO8601 **带时区**（建议 `+08:00`） |
| `assets[].runtime` | 本期只有 `"win-x64"`（以后可能加 `win-arm64`；客户端按自己进程架构挑） |
| `assets[].fileName` | **必须与附件名逐字一致**（客户端靠它去附件列表匹配） |
| `assets[].sha256` | 64 位**小写**十六进制，zip 的实际哈希 |
| `assets[].sizeBytes` | zip 的**实际字节数**（必须与附件大小一致） |
| `assets[].downloadUrl` | **留空字符串 `""`** —— 客户端自己按 `fileName` 去附件列表里匹配填上。**不要**在这里写死 URL |
| `assets[].parts[]` | **可选**（2026-10-06 增补）。分卷时才有：每卷 `{fileName, sha256, sizeBytes}`，数组顺序＝拼接顺序。解析时必须容忍该字段**不存在**（不分卷、以及所有老清单都没有它） |
| `requiresManualMigration` | 本期固定 `false`。写 `true` 客户端会只提示"需要手动更新"而不自动下载 |
| `requiresRestart` | 固定 `true` |
| `releaseNotes` | 空字符串时客户端显示「本次 Release 没有填写更新公告。」 |

## 5. 包内清单 `update-package.json`（打包时生成，**放进 zip**）

```jsonc
{
  "schemaVersion": 1,
  "toolboxStableKey": "GalExcleTools",
  "version": "1.0.1",
  "runtime": "win-x64",
  "entryExe": "TFAC剧情箱-轮椅版.exe",
  "windowsAppSdkRuntime": "2.0",
  "createdAt": "2026-10-05T12:00:00+08:00"
}
```

客户端与 updater 的校验规则（**逐条都会检查**）：

1. zip 里必须能找到 `update-package.json`（递归找）
2. `toolboxStableKey` 必须相等
3. `version` 必须等于清单里声明的版本
4. `runtime` 必须等于客户端进程架构
5. zip 里必须存在**文件名**等于 `entryExe` 的条目（比较时**只看文件名，不看路径**）
6. ★ 该条目的**解压后长度必须 > 0**（空 exe 会被判为坏包）
7. ★★ `windowsAppSdkRuntime`（2026-10-06 新增）：框架依赖的包在这里写 Windows App Runtime 的
   major.minor（例如 `"2.0"`），自包含的包写空字符串。**覆盖器读它做运行前置** ——
   目标机器没有对应运行时（家族 `Microsoft.WindowsAppRuntime.2`，版本 ≥ 2.0）就**中止更新、一个文件都不覆盖**，
   避免把"起不来的新版"装上去。出包脚本按程序目录自动判：有 `Microsoft.WinUI.dll` 但没有
   `Microsoft.ui.xaml.dll` ⇒ 框架依赖；版本号取自 csproj 的 `PackageReference Microsoft.WindowsAppSDK`。

## 6. 发布流程（**顺序不能变**）

```
1) 构建打包
   dotnet publish -r win-x64（PublishTrimmed=false！裁剪会让 WinUI 的反射型 Binding 静默失效）
   ★ 2026-10-06 起 Windows App SDK 走**框架依赖**（`-p:WindowsAppSDKSelfContained=false`）：
     目标机器需装一次 Windows App Runtime 2.0；换来包里少掉 WinUI 运行时那一套（压缩后约 18.5 MB）。
   → 组装出程序目录 → 生成 update-package.json 放进目录 → 压缩成 zip
2) 计算 zip 的 sha256（小写）与 sizeBytes
3) 写 .sha256.txt（"{sha}  {zip文件名}"）
4) 写 toolbox-update.json（此刻 sha256 / sizeBytes 已确定）
5) 幂等确保 Release 存在
     GET  releases?per_page=100        → 按 tag_name 精确匹配
     已存在 → PATCH releases/{id}      （更新 name / body / prerelease）
     不存在 → POST  releases
6) 先传 zip            ← 最大的文件先传，它的失败代价最高
7) 再传 .sha256.txt
8) 复查：GET releases/{id}/attach_files?per_page=100
     确认附件名齐全、大小与本地一致 —— 缺一即【中止】，绝不继续
9) ★ 最后才让清单生效：传 toolbox-update.json
     · 若该 Release 已有旧清单 → Gitee 不允许同名附件 → 必须先
       DELETE releases/{id}/attach_files/{attachmentId} 再 POST
     · 铁律：任何附件上传/校验失败，绝不更新清单
       （清单是客户端唯一入口；清单指着的包没传成功 = 用户拿到一个坏更新）
10) 自检（模拟客户端：匿名、不带 token，**只读一次清单**）
     · GET https://gitee.com/{owner}/{repo}/releases/download/{tag}/toolbox-update.json?t={时间戳}
       → 解析出的 version / channel / 整包 sha256 与本地一致
     ★ 2026-10-06 行为变更（用户定案）：**只读清单** —— 不逐个 HEAD 附件、不打 API、没有退避重试。
       与安卓启动器 Assert-AndroidPublicVersion 同形：成本 659 字节、单次尝试、20 秒超时（快速失败）。
       不想要这一步用 -SkipSelfCheck；读不到但不想判失败用 -TolerateSelfCheckFailure。
     ★★ GitHub 通道**没有**收尾自检：客户端只读 Gitee，而 GitHub 侧上传完已经由带 token 的

       网络一不好就把发布尾巴拖到好几分钟 —— 2026-10-06 实测踩到后整段删除。
```

## 7. 幂等 / 断点 / 取消

- **同一版本重复跑 = 无副作用**：附件同名**且同大小** → 直接跳过上传
- 附件同名但**大小不同** → 先 `DELETE` 再 `POST`（说明上次传坏了或包被重打了）
- ★ **清单类文件（`toolbox-update.json` / `sha256.txt`）例外：每次都重传**（先 `DELETE` 同名再 `POST`）
  —— 它们只有几百字节，绝不冒"同名同大小但内容不同被跳过"的风险（实测踩过：清单字节数恰好没变，
  线上清单于是长期指着旧包）。**不要**为了省这一次请求把清单也按大小跳过。
- 上传中途失败 → 重跑只补缺的，不要重头删光
- 建 Release 要**幂等**：已存在就 `PATCH`，不要重复 `POST`
- **每个网络动作**都要输出结构化进度（供上层 UI 显示 / 取消）：
  `::axtools {"type":"progress","…"}` / `::axtools {"type":"cancellation","mode":"stop"|"locked"}`
- **取消契约分级**：构建 / 上传阶段可以停（`mode":"stop"`）；**提交清单那一瞬间必须 `locked`，不可中断** —— 半套附件 + 已更新的清单是最坏状态

## 8. 上传附件的正确姿势

**必须用 `curl.exe`**，不要用 `Invoke-RestMethod`（PowerShell 传 multipart 在这类接口上不可靠）：

```powershell
curl.exe --fail-with-body --show-error --request POST `
  --form "access_token=$token" `
  --form "file=@D:\path\GalExcleTools-v1.0.1-win-x64.zip;filename=GalExcleTools-v1.0.1-win-x64.zip" `
  "https://gitee.com/api/v5/repos/xiaojie578/TFACStorybox/releases/{id}/attach_files"
```

要点：

- `--fail-with-body` **必须加** —— Gitee 的 403 / 404 **错误正文**才是诊断依据（状态码会骗人，见 §2 第 5、6 条）
- `;filename=` 显式指定附件名，不要依赖 curl 从路径推断
- **上传前**先做 100 MiB 前置检查（§2 第 1 条）
- 实际参数（2026-10-06 起）：
  `--http1.1 --fail-with-body --show-error --retry 10 --retry-delay 5 --retry-all-errors -H 'Expect:'`
  - **不限速**：原来写死 `--limit-rate 1200k`（99.46 MB 至少 85 秒），而"不限速必断"那条结论
    只有 1 个样本、没留复现步骤。真再撞上 `curl: (55) Send failure` 就把 `--limit-rate 1200k` 加回来（一行）。
  - **附件上传不支持续传**：每次重试都从 0 开始，所以是"不限速 + 有限次重试（10 次）"，不是"无限重试"。

## 10. 附件容量管理（1 GB 墙）

- 每次发布后统计本仓库附件总量（附件列表里各条 `size` 求和）
- 策略：**只保留最近 2–3 个 Release 的附件**；更老的**删附件**（保留 Release 页，用户仍能查历史）
- 为什么不能只留最近 1 个：客户端更新失败时的回退窗口是"上一版"，需要上一版的包还在
- 实现：`Publish-GalExcelGiteeRelease.ps1 -KeepReleasesWithAssets 3`（默认 3，`-SkipPrune` 可跳过清理）
- ★ **2026-10-06 增补**：**GitHub 通道不做任何清理**（它没有 1 GB 墙），旧版本永久保留；Gitee 侧仍是"留最近 3 个"。
  两个平台传的是**同一批附件**（分卷时就是同一组卷 + 同一份 `sha256.txt` + 同一份清单）。
- ★★ **2026-10-06 行为变更（用户定案，已实测）**：清理的**触发条件从"附件总量超 1 GB"改成"带附件的 Release 个数超过 `-KeepReleasesWithAssets`"**
  —— 原意就是"只留最近 2–3 个可下载版本"，等撞墙才清的话下一个版本可能已经传不上去了。
  每个被清掉的旧版本依次做三件事：**删附件 → 删 Release 记录 → 删远端 tag**
  （保留记录会留一堆"点进去没文件"的空壳；只删附件的旧行为可用 `-KeepOldReleaseRecords` 找回）。
  - **删 tag 只能走 git**：Gitee 的 v5 API **没有删 tag 的接口** —— `DELETE /repos/{o}/{r}/tags/{name}` 与
    `DELETE /repos/{o}/{r}/git/refs/tags/{name}`，token 放请求头与放查询串**四种组合全是 404**（实测）；
    可用的是 `git push <remote> :refs/tags/<tag>`（实测输出 `- [deleted]`、退出码 0）。脚本里对应 `Remove-ZdGiteeTag`。
  - **只清理不发版**：`Publish-GalExcelGiteeRelease.ps1 -PruneOnly -Version <要保护的版本>`（不出包、不要求产物目录齐备）
  - **令牌**：`FANTASYTOOLS_GITEE_TOKEN` 与 `GALEXCEL_GITEE_TOKEN` 在本机是同一枚（长度 32、指纹一致），
    脚本的查找顺序已按本节建议把 `FANTASYTOOLS_GITEE_TOKEN` 放在最前。

## 11. 交付标准（发布侧做完必须能通过）

- [ ] 一条命令发布一个版本（输入：版本号 / 通道 / 更新公告 / 本地打包目录）
- [ ] **同一条命令重跑两次，第二次无副作用**（附件全部跳过）
- [ ] 发布中途断网 → 重跑能补齐，且**不会留下半套附件 + 已更新清单**的状态
- [ ] 发布完成后**不用 token、不带任何凭据**，能匿名拉到清单并成功下载包（这是客户端的真实路径）
- [ ] 自检**只读一次线上清单**（不打 API、不逐附件 HEAD）—— 匿名配额是 60 次/小时、按 IP 计，要留给客户端
- [ ] 包是 Windows App SDK **框架依赖**形态（目标机器需 Windows App Runtime 2.0）
- [ ] 故意把 zip 重新打包（大小变了）再重跑 → 脚本能识别并替换旧附件
- [ ] 故意让某个附件上传失败 → **清单不被更新**
- [ ] 超过 100 MiB 的包**自动按字节切卷**（每卷 ≤100 MiB），且「按卷号顺序拼接后与整包**逐字节相同**」
      （★ 2026-10-06 起改为自动切卷，**不再**直接拒绝；已实测 4 卷拼接 sha256 与整包一致）
- [ ] 全库搜索（含脚本、日志、产物）**搜不到任何 token 明文**
- [ ] `prerelease` 与版本号后缀一致（`-Beta` → true），有断言或测试兜住

## 12. 明确不要做的事

| ❌ 不要 | 原因 |
|---|---|
| ~~GitHub 渠道 / 第二源 / OSS~~ **（本行 2026-10-06 作废）** | 原需求是"只留 Gitee 一个源"；用户后来明确要求**加上 GitHub 通道**（GitHub 只上传、从不删除）。现行为见 `Docs\热更新-分卷与双通道-契约.md` §6 |
| 断点续传（Range） | Gitee 实测不支持，写了也是白跑一次全量 |
| 用 `releases[].assets` 当附件列表 | 那个字段里是源码归档 zip |
| 把清单当**仓库文件**提交 | 客户端只从 **Release 附件**里读清单；仓库文件对客户端毫无作用 |
| 发 `.exe` / `.apk` 等类型 | 平台会以「无相关资质」拦截 |
| 不带 `per_page` 的列表调用 | 默认只返回 20 条，会漏掉你要找的 Release |
| `!prerelease` 这种写法 | 若字段是字符串 `"false"`，它是**真值** → 通道判定彻底反掉 |
| 把 `-Beta` 版本写成 `prerelease = false` | 测试版会直接推进正式通道 |
| 用 `Invoke-RestMethod` 传 multipart | 不可靠，用 `curl.exe --fail-with-body` |
| 在清单里写死 `downloadUrl` | 客户端按 `fileName` 自己去附件列表匹配；写死了反而会与真实附件不一致 |
| 给清单类文件也按"大小相同"跳过 | 清单字节数可能不变而内容变了，客户端会长期拿到错的哈希（实测踩过）：清单每次重传 |
| 打 `.pdb` / `__pycache__` 进包 | 白占体积，直接顶 100 MiB / 1 GB 两道墙 |

## 13. 增量更新（delta，2026-10-06 新增）

> 起因：整包已经 **76.42 MB**（框架依赖那次瘦身之后），而每版真正变化的只有应用自身那几个文件。
> 实测 **2.1.0 → 2.1.1**：变化 4 个文件（`.dll` / `.exe` / `.deps.json` / `Scripts\热更新覆盖.ps1`），
> 增量包 **3.09 MB**，省 **96%**。2.0.3 → 2.0.4 那次更极端：变化 4 个 + 删除 274 个，增量包 3.11 MB。

### 13.1 出包侧要产出什么

| 产物 | 说明 |
|---|---|
| 整包 `…-win-x64.zip` | **永远发**，兜底 |
| `file-index.json` | 本版文件索引（相对路径 → 大小 + SHA-256）。**留给下一版算增量用**，所以旧 zip / 旧程序目录都不必长期保留 |
| `…-delta-from-v{基准}.zip` | 只装"变化 / 新增"的文件 + 包内清单里的显式删除清单 |

- 基准版**自动选**：产物根下"比本版低、且有 `file-index.json` 或程序目录"的**最高**版本；可用 `-DeltaBaseVersion` 指定。
- `-NoDelta` 可关掉；程序目录被清理时会**优雅退化**为"本版只发整包"（绝不让发布失败）。
- **两条路径都要产出**（全量出包 / 复用已有包）：复用路径会重生成清单，不补 delta 段的话，一次重发就把增量段抹掉。

### 13.2 清单新增字段（`toolbox-update.json`）

```jsonc
"delta": {
  "baseVersion": "2.1.0",             // 本机版本必须正好等于它，否则不能用这个增量包
  "fileName": "GalExcleTools-v2.1.1-win-x64-delta-from-v2.1.0.zip",
  "sha256": "…", "sizeBytes": 3200000,
  "changedCount": 4, "deleteCount": 3
}
```
老客户端不认识这个字段 → 直接忽略、走整包（**向后兼容**）。

### 13.3 发布链要做的

- 增量包作为一个**额外附件**上传（Gitee + GitHub 都传），并纳入"附件名 + 大小"复查。
- 上传前校验：大小与 `delta.sizeBytes` 一致、SHA-256 与 `delta.sha256` 一致、不超过单附件 100 MiB。
- **公告为空时自动补一句**（出包脚本写进清单、发布库用它当 Release 正文兜底）：
  `本次更新：增量包 3.09 MB（变化 4 个文件 / 删除 3 个）；完整包 76.42 MB。`

### 13.4 边界（都要稳住）

| 情况 | 行为 |
|---|---|
| 逐文件完全相同 | **不发**增量包（"无变化"） |
| 估算增量 > 整包的 70% | **不发**增量包（直接发整包更省事） |
| 本机版本 ≠ 基准版（跨版升级 / 上次没更完） | 客户端下**整包** |
| 增量包比整包还大 / 清单字段写坏 | 客户端下**整包** |
| 本机文件被手改过、或与包内旧内容指纹对不上 | **中止，一个文件都不动** → 回落到整包 |
