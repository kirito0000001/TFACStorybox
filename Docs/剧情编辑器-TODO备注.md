## 0. 结论摘要

1. **备注和剧情文本是"同一种东西"，只是存到不同文件。** 这条是全部设计的地基 ——
   凡是"备注要不要自己一套 X"的问题，答案都是"不要，跟剧情文本一样"。
2. **它的难点不是功能，是时序。** 六次返工里有五次是 WinUI 的"事件 / 绑定 / VM 属性"
   三者先后顺序问题，一次是自造指示灯把真相盖住了。功能代码本身不到 100 行。
3. **调试期间只能有一个"真相来源"。** 我给备注面板另造了一个状态行，
   它写着"已保存"而实际一个字都没存进去 —— 于是我和用户都看不见 bug。
4. **能看数据就别猜。** 最后定位靠的是用户去看了一眼 `story-todos.json`：
   文件写成功了、时间戳会动、JSON 结构也对，**只有 `Notes` 是空的**。
   这一条信息直接排除了"触发""写盘""序列化"三个方向。

## 1. 界面与交互

右栏（`MainWindow.xaml`，在「行与小节」下面）新增一个 `Expander`：

```
▼ TODO 备注
  ┌────────────────────────────┐
  │ 给这一句写个备注…（回车换行）│   ← AcceptsReturn=True，回车**就是换行**，不拦截
  └────────────────────────────┘
  ☐ 第 45 句 · WHK-M1 · 第 2 小节          [跳过去]
     这里要改成"猎头网站"的正式说法
  ☑ 第 12 句 · WHK-M1                     ← 勾掉 = 已处理，只灰显、不重排
```

几个刻意的取舍：

| 决定 | 理由 |
|---|---|
| **回车是换行，不做提交** | 备注常要写好几行；拿回车当提交会让它没法用 |
| **没有「保存」按钮** | 走编辑器本来那套 debounce（350ms），和剧情文本共用同一个计时器 |
| **状态只用右上角那个** | 不另造 —— 见 §4.5，造过一次，它在撒谎 |
| **勾掉只灰显、不重排** | 每勾一下整张列表都跳会让人找不到东西 |
| **清空文本框 = 删掉这条备注** | 留一条空备注只会让列表变成噪音 |
| **跨章跳转可用** | 备注列表是整个项目的；"回头找回来"时没人记得它在第几章 |
| **列表按章节 + 行号稳定排序** | 稳定排序才好找；重排是反效果 |

## 2. 数据与文件

**落点**：`<工具项目>/Tools/story-todos.json`（和 `unreal-sync-state.json` 同一个目录）

```json
{
  "Version": 1,
  "Notes": [
    {
      "ChapterCode": "WHK-M1",
      "RowNumber": 45,
      "Section": 2,
      "Text": "这里要改成\"猎头网站\"的正式说法",
      "Done": false,
      "UpdatedAt": "2026-10-14T14:24:45+08:00"
    }
  ]
}
```

**为什么是旁挂文件而不是写进 CSV**：剧情 CSV 是要**导出给 Unreal** 的
（同步会把它变成数据表）。往里面加一列备注，那一列会跟着同步进工程 ——
备注是给工具箱自己看的，不该跑到游戏里去。

**为什么定位只认「章节 + 行号」**：
- `Section` **只存不用**（只作显示）。小节会被重新拆分（「创建新小节」就是把当前句拆出去），
  拿它当键的话，每拆一次小节那一章后面的备注就全成孤儿了。
- 行号会漂（中间插句 / 删句），但它是编辑器本身的稳定口径 ——
  真漂了就按列表里的行号去对，好过为了"永不漂"引入一套更复杂的东西。

**读写都不抛**：文件坏了、没权限、JSON 半截 —— 一律当成"没有备注"，
绝不让它把剧情编辑器搞挂。（和日志文件同一个规矩。）

## 4. 踩过的坑（★ 这一节比上面的代码值钱）

### 4.1 「备注一个字都存不了」——计时器不会被顺带触发

**我的错**：在备注的 `TextChanged` 里只标脏，注释里写"存盘走编辑器本来那套 debounce"。

**根因**：`_storyEditSaveTimer` 只在**剧情行**编辑时被 `ScheduleStoryRowSave` 启动。
只往备注框里打字的话，它**根本没跑过**。

**正确做法**：谁改的东西，谁负责把计时器踢起来。现在直接调 `ScheduleStoryRowSave`（同一个入口）。

---

### 4.2 「备注跑到下一句去了」——在控件事件里读文本，读得太早

**我的错**：在 `TextChanged` 里读 `_storyEditorViewModel.TodoText` 并立刻写数据。

**根因**：`TextChanged` 是**控件自己的事件**，它比 TwoWay 绑定把新值推给 VM **更早**。
在那里读到的是**上一次的旧值**。

剧情文本的做法：`TextChanged` 里只标脏 + 启动计时器，**350 毫秒后**才在
`SaveCurrentStoryRow` 里读 `StoryText` —— 那时候绑定早就推完了。

**正确做法**：读取放在保存那一刻（`SaveStoryTodosIfDirty` 开头）。

---

### 4.3 「切句子还是丢了」——落点跟着 `_currentStoryRowIndex` 漂

**我的错**：应用文本时用 `_currentStoryRowIndex` 决定写到哪一句。

**根因**：`LoadStoryRowIntoUi` 跑的时候 `_currentStoryRowIndex` **已经是新行**了，
而文本框里还是**旧行**的内容 —— 按"当前行"写，就把旧行的字写到新行上。

**正确做法**：落点只认**载入时记下的那一句**（`_storyTodoEditingChapterCode` /
`_storyTodoEditingRowNumber`，在 `LoadStoryTodoIntoUi` 里"先记再改 `TodoText`"）。

> **4.2 和 4.3 必须一起修，单做哪条都不行**：
> - 只做 4.2（挪到存的时候读）→ 落点还是跟下标漂；
> - 只做 4.3（记住是哪一句）→ 读到的还是过期值。
>
> 我两种单用各翻过一次车，表现分别是"还是丢了"和"跑到下一句去了"。

---

### 4.4 「数据被自己盖掉」——让两处互为来源

**我的错**：保存时 `CollectStoryTodoNotesFromRows()` —— 从**列表行**里读回全部，
再赋值给 `_storyTodoNotes`。

**根因**：行是**刷新列表时建的快照**。打字加进 `_storyTodoNotes` 的那条**不在快照里**，
保存时拿快照反过来盖一遍，刚写的就没了。

**正确做法**：`_storyTodoNotes` 是唯一数据源；行里唯一"比数据新"的只有 `Done`
（勾选框双向绑在行上），所以保存前**只收 `Done`**（`MergeStoryTodoDoneStateFromRows`）。

> 一句话：**谁的字段谁负责，别互相盖。**

---

### 4.5 「造了一个会撒谎的指示灯」——自造第二个状态显示

**我的错**：在备注面板底下加了一行 `TodoStatusText`，写着「还没有任何备注 · 已保存」。

**根因**：实际一个字都没存进去 —— **它在撒谎**。于是我看不见 bug，
用户也看不见，连着五版都在盲修。

用户的原话：

> 「你自己给备注底下新建了一个变化，你把那个去掉，我猜你是以为那个是正确的」

**正确做法**：删掉它，改用编辑器本来就有的 `SaveStatusText`（右上角那个）：
存之前「等待保存...」，存完「已保存 HH:mm:ss」—— 和剧情文本同一个词、同一处显示。

> **调试期间只能有一个"真相来源"。** 第二个指示灯比没有更糟 —— 它把真相盖住。

---

### 4.6 「文件写成功了，但 Notes 是空的」——从 VM 属性读字

**现象**（用户去看了一眼文件，我也去看了）：

```
story-todos.json   36 字节   14:24:45    ← 写盘**成功了**，时间戳会动
{ "Version": 1, "Notes": [] }             ← 但内容是**空的**
```

**根因**：`RefreshStoryTodoPanel` 载入某一句时会把它设成那一句的备注（没备注就是空串）。
于是"**程序设成空串**"和"**用户真的清空了**"在 VM 属性上**长得一模一样**，
从属性上根本分不出来。

**正确做法**：`TextChanged` 里顺手把**控件里的字**抓下来（`sender as TextBox` →
`_pendingStoryTodoText`），保存时优先读这份；载入某一句时把这份也同步成"这一句该有的内容"
（这样迟到的保存写回去等于空操作）。

> 一句话：**VM 属性可以被程序改写，控件内容只由用户改写 ——
> 要判断"用户想写什么"，只能看后者。**

## 5. 可复用的经验（写 README / 做下一个功能时看这里）

1. **"跟剧情文本做成同一种"是最省事的设计。** 它已经把载入 / 触发 / 存盘三件事
   都趟平了；另起一套就要把这三件事各重做一遍，而每一件都有 §4 里那种时序坑。

2. **复用现成机制时，必须验证它的触发条件。** "共用同一个计时器"不等于
   "它会被顺带触发"（§4.1）。把功能建在一个**永远不会发生的**前提上，
   表现是"完全不能用"，不是"偶尔丢一点"。

3. **WinUI 里"控件事件"早于"绑定推值"。** 要读用户输入，两个选择：
   - 从**控件**读（`sender as TextBox`）；
   - 或者等一拍再读 **VM 属性**（剧情文本就是这么做的）。
   **千万别在控件事件里立刻读 VM 属性**（§4.2）。

4. **"程序设的值"和"用户设的值"要能分辨。** 同一个空串，来源不同、含义不同（§4.6）。
   解法是**多存一份来自控件的**，而不是继续猜属性。

5. **一个界面只留一个状态来源。** 自造的第二个指示灯会掩盖真相（§4.5）。

6. **能看数据就别猜。** §4.6 定位靠的就是打开那个 JSON 看一眼 ——
   一次观察排除了"触发""写盘""序列化"三个方向。**让用户去看文件，
   比让用户描述现象有效得多。**

7. **先读现成的那条路，再动手。** 这个功能返工六次，前四次都是"没读代码就开始加东西"
   （加计时器 → 加记忆字段 → 加合并 → 加状态行）。读完之后改动反而都是**减法**。

## 6. 已知限制 / 以后可以做的

- **行号会漂**：中间插句 / 删句之后，备注记的行号会指向别处。目前靠列表里的
  「第 N 句 · 章节 · 小节」自己认。真要做到不漂，得给每句一个稳定 id（列进 CSV 或另存映射）。
- **跨章跳转会切章**：走的是 `ShowStoryEditorPageAsync`（它开头就会存当前行并 flush），
  所以不会丢编辑。章节改名 / 删掉时会在状态里说明，不装作跳过去了。
- **没有搜索 / 过滤**：备注多了以后需要（比如"只看未处理""只看本小节"）。
- **没有导出**：以后写 README 时可能想把待办导成一份清单。
