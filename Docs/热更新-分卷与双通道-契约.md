# 热更新：分卷下载与双通道发布 · 契约（2026-10-06 定案）

> 本文是 `Docs\热更新-发布侧需求.md` 的**增补**。两者冲突时**以本文为准**。
> 触发原因（用户定案，原话）：*"不用做成热更新那种需要前置条件的，把文件拆开来就行了。然后还是把 github 也加上吧，gitee 的 release 只保存最近三个，完整发布的时候会删除旧的。github 那边就正常上传不用删除。"*

## 0. 一句话

发布侧现在会**按字节把整包切成若干卷**（只在整包超过 Gitee 单附件 100 MiB 时才会切），
并**同时发到 Gitee 与 GitHub 两条通道**；客户端要做的只有一件事：
**按清单里的顺序把各卷拼回整包，再按老规矩校验整包。**

---

## 1. 什么时候会分卷

| 情况 | 产物形态 |
|---|---|
| 整包 ≤ 100 MiB（当前约 99.5 MB，走框架依赖后会更小） | **不分卷**，与历史完全一致：单个 `…-win-x64.zip` |
| 整包 > 100 MiB | 自动按每卷 **90 MB** 切分（`-PartSizeBytes` 可改；2026-10-06 从 95 MB 改小），附件名见 §2 |

> 编号上限 99 卷（两位数字）。切到 99 卷意味着包接近 10 GB，那时该换发布方式而不是继续切。

**分卷是"整包超墙"时的兜底，不是默认形态。** 90 MB/卷意味着整包涨到 180 MB 都还是 2 卷，
且每卷离 100 MiB 有 10 MiB 余量。下个版本一旦越线就会自动切 —— 客户端必须早就支持它，否则那次更新会直接失败。

> ★ **2026-10-06 定案（下发前必读）**：清单里**不再有"最低支持版本"这种东西**
> （`minSupportedVersion` 已从清单结构、发布脚本、客户端三处一起删除）。
> 原因：那是个反直觉的闸门 —— 一个**自动推导**出来的版本号就能把所有人的自动升级关死。
> 实际踩过两次：v2.0.3 被算成 **2.0.2（从未发布）**，v2.0.4 又被算成 **2.0.3**，两次都把 2.0.0/2.0.1 拦在门外。
> 现在的原则是**旧版兼容**：新版本自己负责让老客户端吃得下去。
>
> 分卷这边同理，只需要知道一件事：实测 `parts` 支持是 **2.0.1 起**才有的（2.0.0 没有，直接扫已发布客户端的
> `TFAC剧情箱-轮椅版.dll` 确认）。所以**第一个分卷版本会让 2.0.0 失败** —— 但它失败得看得懂：
> 「清单里的 {fileName} 在 Release 附件里找不到，请手动下载。」用户手动装一次即可，不会静默坏掉。

## 2. 附件名与数量

整包文件名不变，卷名 = **整包名去掉扩展名 + `.partNN` + 原扩展名**（`NN` 从 `01` 起、两位零填充）：

```
GalExcleTools-v2.1.0-win-x64.zip          ← 整包（分卷时**不再上传它**，但清单里仍指向这个名字）
GalExcleTools-v2.1.0-win-x64.part01.zip
GalExcleTools-v2.1.0-win-x64.part02.zip
…
GalExcleTools-v2.1.0-win-x64.sha256.txt
toolbox-update.json
```

- ★ 扩展名**故意保留 `.zip`**：平台会按文件类型拦下载，`.zip` 最不容易被拦（需求 §2 第 11 条）。
- ★ **拼接顺序 = 文件名升序 = 清单里 `parts[]` 的数组顺序**，三者必须一致。
- 分卷时整包本身**不作为附件上传**（否则附件总量白白翻倍，撞 Gitee 的 1 GB 仓库墙）。
- 一个 Release 里**绝不能有两个同名附件**（`toolbox-update.json` 恒定同名，客户端按名字找它）。

### 2.1 `….sha256.txt` 是可变的行数

| 形态 | 内容 |
|---|---|
| 不分卷 | **单行**：`{整包sha256}  {整包文件名}`（sha256sum 风格，**两个空格**）+ 结尾换行 |
| 分卷 | **第 1 行仍是整包**（即"拼接后应当得到的哈希"），随后**每卷一行**，顺序同卷号 |

★ 客户端**不要**假设它只有一行；但也**不要**用它的行数去推断要不要分卷 —— 以清单里的 `parts[]` 为准。

## 3. 清单 `toolbox-update.json`：新增可选字段 `parts[]`

```jsonc
{
  "schemaVersion": 1,
  "toolboxStableKey": "GalExcleTools",
  "version": "2.1.0",
  "channel": "stable",
  "assets": [
    {
      "runtime": "win-x64",
      "fileName": "GalExcleTools-v2.1.0-win-x64.zip",   // ← 恒为**整包**名
      "sha256": "dd7d813b…",                                  // ← 恒为**拼接后整包**的哈希
      "sizeBytes": 104277589,                                 // ← 恒为**拼接后整包**的字节数
      "downloadUrl": "",
      "parts": [                                              // ← 只在分卷时出现；不分卷时**整个字段不存在**
        { "fileName": "GalExcleTools-v2.1.0-win-x64.part01.zip", "sha256": "bc00d3d9…", "sizeBytes": 31457280 },
        { "fileName": "GalExcleTools-v2.1.0-win-x64.part02.zip", "sha256": "149f89e0…", "sizeBytes": 31457280 },
        { "fileName": "GalExcleTools-v2.1.0-win-x64.part03.zip", "sha256": "8cf4a685…", "sizeBytes": 31457280 },
        { "fileName": "GalExcleTools-v2.1.0-win-x64.part04.zip", "sha256": "bfac9260…", "sizeBytes": 9905749 }
      ]
    }
  ]
}
```

**铁律（写错客户端就会下错东西）**：

1. `assets[].fileName` / `sha256` / `sizeBytes` **永远是整包**的语义，**不是**任何一卷的 —— 分卷时它们描述"拼起来之后应该得到什么"。
2. `parts[]` **只在分卷时存在**。解析时必须按"字段可能不存在"处理（`TryGetProperty`），不要用"读不到就抛异常"的写法。
3. `parts[].sha256` / `sizeBytes` 是**该卷自己**的哈希与大小（客户端可以逐卷校验，提前发现坏卷）。
4. `downloadUrl` 仍然留空字符串 —— URL 由客户端按 `fileName` 去 Release 附件列表里匹配。

## 4. 客户端下载与拼接（要实现的算法）

```
payloads = parts 非空 ? parts : [ { fileName, sha256, sizeBytes } ]   // 不分卷就是"一卷=整包"

1) 按 parts 顺序逐个下载到同一个临时文件（追加写）：
   for each p in payloads:
       下载 p.fileName 对应的附件
       边写边算该卷 sha256，写完比对 p.sha256 与 p.sizeBytes     ← 逐卷校验，坏卷立刻重下
       任一卷失败 → 整次下载失败（不要留下"拼了一半"的文件当成品）

2) 拼接完成后，对**整个文件**算 sha256，比对 assets[].sha256
   并比对 总长度 == assets[].sizeBytes                         ← 这一步与老版本完全一致，不能省

3) 通过后才改名成正式包名（如 ….zip），交给覆盖器（Scripts\热更新覆盖.ps1）
```

实现要点（踩过的坑，照做就行）：

- **顺序拼接是字节级追加**，不是"解压后合并" —— 各卷不是独立可用的 zip，**单独解开某一卷没有意义**。
- 临时文件继续用现有的 `.download` 后缀与 `Updates\` 目录，**复用现有的残留清理与缓存逻辑**：
  缓存里已有一个**校验通过**的包就直接用；只有"校验通过"才算数，
  **绝不能**把"卷下齐了但没拼"或"拼完没校验"的状态当成可用包。
- 逐卷校验 + 整包校验，两道都要。逐卷那道是为了"一卷坏了只重下那一卷"，
  整包那道是为了"顺序/边界错了能被发现"。
- 拼接时用 `FileStream` 追加 + 4 MB 缓冲（30 MB 一卷，一次读完也行，别再大）。

## 5. 老客户端会怎样（必须知道）

老客户端只认 `assets[0].fileName`，在分卷 Release 的附件列表里**找不到**那个整包名 → 下载失败。

- **不分卷时完全无影响**（老客户端照旧）—— 这就是"分卷只在超墙时才发生"的价值。
- **一旦分卷，不支持 `parts` 的老客户端（实测只有 2.0.0）会更新失败** —— 但它失败得**看得懂**：
  客户端会提示「清单里的 {fileName} 在 Release 附件里找不到，请手动下载。」（§7.2 的文案），
  用户手动装一次即可，不会静默坏掉。
- ★ 2026-10-06 定案：**清单里不再有"最低支持版本"这种东西**（`minSupportedVersion` 已从清单、发布脚本、
  客户端一起删除）。原则是**旧版兼容**：新版本自己负责让老客户端吃得下去，而不是靠一个自动推导的闸门把老版本关在门外。

## 6. 两条通道（Gitee + GitHub）

| | Gitee | GitHub |
|---|---|---|
| 附件 | 同一批（同样的卷名、同样的 `sha256.txt`、同样的清单） | **同一批**，逐字节相同 |
| 旧版本 | **只保留最近 3 个带附件的 Release**；更老的**删附件 → 删 Release 记录 → 删远端 tag**（`-KeepOldReleaseRecords` 可只删附件） | **从不删除**，永久保留 |
| 为什么要这样 | 每仓库附件合计只有 1 GB | 没有这条约束，所以保留全部历史更省心 |
| 单附件上限 | 100 MiB | 2 GiB |

客户端注意：

- 两个平台**是同一批产物**（同一次出包、同一份清单），所以**一次更新必须只来自同一个 Release**；
  不要"清单读 Gitee、包下 GitHub"地混着用 —— 虽然内容相同，但那是巧合而不是保证。
- `releaseNotesUrl` 目前仍指向 Gitee（历史行为，客户端只用它做"查看公告"跳转）。
- GitHub 侧保留了全部历史版本，将来要做"回退到更早版本"时有更宽的窗口；但**回退窗口仍以 Gitee 的最近 3 个为准**，不要依赖 GitHub 做默认回退源。

## 7. 发布侧怎么跑（供对照，客户端不用管）

```powershell
# 完整发布（Gitee + GitHub；Gitee 侧自动清理旧版本，GitHub 侧只上传、从不删除）
.\Scripts\Publish-GalExcelRelease.ps1 -Version 2.1.0 -ExcludeAiRuntime -Notes "更新公告"

# 演练：只做本地校验 + 打印两条通道的计划，不碰网络
.\Scripts\Publish-GalExcelRelease.ps1 -Version 2.1.0 -ExcludeAiRuntime -DryRun

# 只发一条通道
.\Scripts\Publish-GalExcelRelease.ps1 -Version 2.1.0 -SkipGitee
.\Scripts\Publish-GalExcelRelease.ps1 -Version 2.1.0 -SkipGithub

# 只清理旧版本、不发版（-Version 是要**保护**的那个版本，它自己的附件不会被删）
.\Scripts\Publish-GalExcelGiteeRelease.ps1 -Version 1.0.1 -PruneOnly -KeepReleasesWithAssets 3

# 清旧版本时只删附件、保留 Release 记录与 tag（默认是连记录带 tag 一起删干净）
.\Scripts\Publish-GalExcelRelease.ps1 -Version 2.1.0 -KeepOldReleaseRecords
```

单通道脚本仍在：`Publish-GalExcelGiteeRelease.ps1` / `Publish-GalExcelGithubRelease.ps1`（可独立跑）。

★ **2026-10-06 起发布链结构**：两条通道的实现与共享工具都在 `Scripts\GalExcelPublish.ps1`，
三个入口（编排 + 两个单通道）都是**薄壳**：收参数 → 调 `Invoke-ZdGiteePublish` / `Invoke-ZdGithubPublish` → 用返回值当退出码。
编排层**在同一个进程里**顺序调用两条通道（不再起子进程、不再转发 stdout），进度由 `Set-ZdProgressRange` 映射到 0–50 / 50–100。
部署时 `Scripts\` 整个目录要一起带过去（`GalExcelPublish.ps1` 是新增文件）。

- 只重写清单、不重打包：任何一次发布在"包体复用"时都会**自动把清单重生成一遍**（几百字节、约一秒），
  所以改了清单生成逻辑之后，重跑一次同版本发布即可，不需要重建 76 MB 的包、也不会重传包体。
- 想自测分卷链路：任一发布/出包脚本传 `-PartSizeBytes 30MB`，会把整包切成 4 卷。

**Gitee 清理口径（2026-10-06 起）**：带附件的 Release 超过 `-KeepReleasesWithAssets`（默认 3）就清理最旧的，
每个旧版本依次 **删附件 → 删 Release 记录 → 删远端 tag**。
其中删 tag 只能走 `git push <remote> :refs/tags/<tag>` —— Gitee 的 v5 API **没有**删 tag 的接口（实测全 404）。

## 8. 增量包契约（delta，2026-10-06 新增）

### 8.1 为什么是"文件级增量包"而不是"按清单逐文件下载"

Gitee **不支持 Range**（实测：`-r 0-1023` 请求同一个包，服务端回整个 104,293,807 字节，且无 `Accept-Ranges`）。
所以"只取文件里变化的那几段"（块级增量）在 Gitee 上做不到；逐文件下载又要为每个文件发一次请求、各拿一次附件 URL
（附件 URL 必须从 API 取），成本和失败面都成倍。

**定案**：变化文件**打成一个 zip**，客户端只下**一个**附件。
判定粒度 = 文件；传输粒度 = 一个包；校验粒度 = 两层（外层整包 SHA-256 + 包内每个文件的新旧两个哈希）。

### 8.2 增量包内的 `update-package.json`

```jsonc
{
  "schemaVersion": 1,
  "toolboxStableKey": "GalExcleTools",
  "version": "2.1.1",
  "runtime": "win-x64",
  "entryExe": "TFAC剧情箱-轮椅版.exe",     // 仍然写，但**增量包里通常没有这个文件**（它没变就不进来）
  "windowsAppSdkRuntime": "2.0",
  "delta": true,
  "baseVersion": "2.1.0",
  "files": [
    { "path": "TFAC剧情箱-轮椅版.dll", "sizeBytes": 7462912, "sha256": "…", "baseSha256": "…" }
    // baseSha256 = **旧内容**指纹；新增文件没有这一项
  ],
  "delete": ["onnxruntime.dll", "Microsoft.ML.OnnxRuntime.dll", "DirectML.dll"]
}
```

- `files[]` 就是"包里装了哪些文件"的权威清单，`delete[]` 是"相对基准版被移除的文件"。
- **镜像语义在增量模式下必须关掉**：整包模式下"安装目录里有、包里没有"= 该删；增量模式下那些文件只是**没变**，
  一个都不许动。删除项只认 `delete[]`，而且**照样先过镜像白名单**。

### 8.3 客户端选择规则（只有一条 if）

```
delta 段存在？
├─ 没有                                    → 整包
├─ 本机版本 ≠ delta.baseVersion             → 整包
├─ delta.sizeBytes ≥ assets[0].sizeBytes    → 整包
└─ 其余                                    → 增量包（只下这一个）
```

### 8.4 覆盖器的两道前置闸门（任一不过 → 中止，一个文件都不动）

| 闸门 | 判定 | 退出码 |
|---|---|---|
| 版本对齐 | `-CurrentVersion` 必须逐字等于包内 `baseVersion` | 1 |
| 旧内容指纹 | `files[].baseSha256` 逐个与本机文件比对（文件缺失也算不符） | 3 |

对不上就是"差异集不成立"，唯一正确的动作是**别动**——客户端随后回落到整包下载。

### 8.5 与既有机制的复用

增量与整包在覆盖器里**共用同一套**两阶段替换、回滚窗口（`*.old-{版本}`）、一键修复脚本、运行时前置（§9.10）。
增量没有自己的一套落地逻辑，这是这个设计最省心的地方。
