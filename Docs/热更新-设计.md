## 0. 六条必须知道的结论

源项目那套「Release 清单 → 下载校验 → 独立 updater 覆盖 → 重启」的骨架可以直接搬，但有六处**必须改**：

| # | 改动 | 为什么 |
|---|---|---|
| 1 | **删掉 GitHub 整条线（客户端侧）** | 你的要求：只留 Gitee。2026-10-06 发布侧把 GitHub 加成了**镜像通道**（同一批字节、同一份清单），但《热更新-分卷与双通道-契约.md》§6 明确要求客户端**一次更新只能来自同一个 Release**（不许"清单读 Gitee、包下 GitHub"）→ 客户端依旧只读 Gitee（§6.1 的分卷增补） |
| 2 | **删掉断点续传** | 实测 Gitee CDN（入口 URL 和落地 URL 都）完全忽略 `Range`，永远 200 整包；源实现「先发 Range、发现不是 206 再删文件重下」= 每次更新白跑一趟 100MB |
| 3 | **Release 列表请求必须带 `?per_page=100`** | 实测默认只返回 20 条 → Release 一多就静默截断，正式版通道会挑到旧版本 |
| 4 | **`prerelease` / `assets` 必须防御性解析** | 官方 swagger 声明它们是 `string`，实测是 bool / 数组 → 不能按文档写强类型 |
| 5 | **必须做请求预算（间隔 + 剩余量 + 失败语义）** | 匿名配额 60、IP 绑定、403 后 20 分钟不恢复 → 一次误触发能让整个 IP 长时间不可用 |
| 6 | **不要用 `cmd.exe` 中转启动 updater** | 本程序 exe 名 `TFAC剧情箱-轮椅版.exe` 含全角冒号、安装路径可能带中文 → `.cmd` 的 encoding/引号在这两点上不可靠；改用 `ProcessStartInfo.ArgumentList` 直接起 `powershell.exe` |

另外三个本仓库特有的约束会反复出现：

- **`MainWindow.xaml` 是 5675 行、棘轮上限正好 5675，零余量**。新增任何一行都要抬上限并在棘轮注释里写理由。
- **`ViewModels/SettingsViewModel.cs` 的 `SetSettingProperty` 只有 `bool` 重载，撤销记录 `SettingUndoEntry` 也只存 `bool`** → 更新通道（枚举）不能直接进撤销栈，见 §12。
- **更新包体积直接决定可行性**：Gitee **单附件 ≤100MiB**，且 **每个仓库的附件总容量 ≤1GB**（见 §4.8）。本工程内置 CPython 3.13 + Pillow，包会很大 → 这既是 RID 决策的依据（§19），也是发布策略的硬约束（附录 B）。
- **安装目录在运行时确实会被写**：`Tools\**\*.py` 跑过一次就会生成 `__pycache__\*.pyc`（本仓库现存 4 处）。所以镜像白名单必须**显式排除 `__pycache__`**，打包侧也要排除（§9.6）。
- **更新包一旦超过 100 MiB，发布侧会把它分卷**（`…partNN.zip` + 清单 `assets[].parts[]`，2026-10-06 起）——当前包 104,277,589 字节，离 100 MiB 只剩 58 万字节，**下个版本几乎必然分卷**。客户端要能按顺序拼回整包，并且做**两道**校验（逐卷 SHA-256 + 拼完整体 SHA-256），见 §6.1 / §8.1。

## 1. 目标与非目标

### 1.1 目标（本次范围）

1. 用户能在**整体设置页**看到当前版本号、更新通道，并手点「检查更新」。
2. 程序按通道（正式版 / 测试版）向 **Gitee Releases** 查询，选出**最新可用版本**；查询匿名进行（实测无需 token）。
3. 发现新版本时给出确认对话框：当前版本、新版本、通道、包名、包大小、更新公告。
4. 确认后：下载 → 校验大小 / SHA-256 / 包内结构 → 启动独立 updater（可见 PowerShell 窗口）→ **等 updater 预检通过** → 主程序退出 → updater 覆盖程序目录 → 重建快捷方式 → 启动新版本。
5. 全流程可取消、有进度、有日志；**在最坏情况下用户手里始终有一个能双击起来的旧版本**。

### 1.2 明确不做（本次）

- **不做**界面上的「开发者发布中心」（打包/发布按钮那套，源项目有，本仓库不要）。

- **不做** GitHub 任何东西（不查询、不展示、不留兼容开关）。

### 1.3 非功能要求（来自 README 硬规矩）

- Service 层不许静默吞异常：每个 `catch` 要么抛，要么 `ToolboxLog.Warn/Error` 记一行说明为什么吞。

## 2. 源方案解剖（FantasyTools 做了什么）

### 2.1 六段链路

```
① 检查   CheckAsync(source, channel, timeout, ct)
         └ 拿 Release 列表 → 按通道挑一条 → 下载 toolbox-update.json → 比版本
② 提示   PromptAndInstallUpdateAsync(result) → ContentDialog
③ 下载   DownloadAndVerifyAsync(manifest, asset, progress, ct)
         └ 复用缓存包 / 断点续传 / 128KB 缓冲 / 大小校验 / SHA-256 / 包结构校验
④ 启动   LaunchUpdaterAsync(packagePath, ...)
         └ 生成 RunUpdate-*.cmd → 起 cmd.exe → 等 ReadySignal（≤90s）
⑤ 预检   热更新覆盖.ps1：参数校验 → SHA 复核 → 解压 staging → 找 update-package.json
         → 写 READY → **主程序这时才 Application.Current.Exit()**
⑥ 覆盖   等主进程退出（≤30s）→ 复制文件 → 删 staging → 重建快捷方式 → Start-Process 新 exe
```

### 2.2 三个值得学的设计（保留）

- **READY 握手**：主程序**不主动**退出，而是等 updater 把「参数校验 + SHA 复核 + 解压 + 清单校验」全做完、写出 `READY` 之后才退出。这样「预检失败」时用户手里还是一个完整可用的旧版本，而不是一个已经退出的程序。
- **三层校验**：附件大小 → SHA-256 → 包内 `update-package.json`（`toolboxStableKey` / `version` / `runtime` / `entryExe` 四项对齐）。防的不是攻击，是**半截包**和**发错包**。
- **覆盖而非镜像**：`Copy-DirectoryContents` 只覆盖和新增，从不删除目标目录里包中没有的文件。
  ⚠️ **v1.1 修正**：这一条**不建议照抄**，见 §9.6——WinUI 3 自包含目录是「版本一致性整体」，残留旧 dll 与新 dll 混用会直接崩。

### 2.3 该丢掉的

| 源实现 | 处理 | 理由 |
|---|---|---|
| `UpdateSource { GitHub, Gitee }` 枚举 + 更新源下拉框 | **删** | 只留 Gitee |
| `GitHubReleaseApiUrl` / `GetGitHubReleaseAsync` / `GitHubReleaseAsset` | **删** | 同上 |
| `GitHubRelease.PrereleaseValue`（`JsonElement` 兼容 bool/string） | **保留思路，改挂到 GiteeRelease 上** | v1 曾判断 Gitee 不需要，**实测+文档比对后推翻**：swagger 声明 string、实测 bool，必须两个都吃（§4.7） |
| `GetResumableDownloadBytes` + `RangeHeaderValue` + 「非 206 就重下」 | **删** | Gitee 入口与落地 URL 都不支持 Range（§4.4） |
| 生成 `RunUpdate-*.cmd` + `cmd.exe /c` | **改** | 中文 exe 名/路径（§9.3） |
| `TryUseExistingPackageAsync`（已下完的包复用） | **保留** | 100MB 重下很痛，校验通过就复用 |
| `CleanUpdateCache`（`*.download` + 保留最近 2 个包） | **保留** | 磁盘卫生 |
| `MeasureConnectionAsync`（测试连接 + 计时） | **保留** | 排查「连不上」很有用；只有 Gitee 一个源，文案相应简化 |
| `HttpClient.Timeout = InfiniteTimeSpan` + 每操作显式 `CancellationTokenSource` | **保留** | 100MB 包在慢网下必然超过 HttpClient 默认 100 秒 |
| `Expand-Archive -Force` 解压 | **改** | 对大量小文件极慢（本包内含 CPython 全套），且 .NET Framework 版 `ExtractToDirectory` 无 zip-slip 校验（§9.4） |
| 「没有清单就从 `.zip + .sha256.txt` 反推清单」的兜底 | **不要** | 我们没有历史包袱，硬要求每个 Release 都挂清单，少一条分支少一类 bug |

## 4. Gitee 实测结论

> 样本仓库：`xiaojie578/FantasyTools`（同一 Gitee 账号）。方法：本机直接发匿名请求，无 token、无 Cookie；本机走 HTTP 代理。

### 4.1 只读接口全部匿名可用

```
GET /api/v5/repos/{owner}/{repo}/releases?per_page=100              → 200，匿名可读
GET /api/v5/repos/{owner}/{repo}/releases/{id}/attach_files?per_page=100 → 200，匿名可读

创建 Release / 上传附件                                              → 需要 access_token
```

### 4.3 ★ 默认分页 = 20 条

| 仓库 | 裸请求 | `?per_page=100` |
|---|---|---|
| `mindspore/mindspore` | **20** | 55 |
| `y_project/RuoYi` | 19 | 19（总数就是 19） |

`?per_page=2&page=2` 能取到第 2 页 → 分页参数有效。

响应头里还带 `total_count` 和 `Link: <...page=0&per_page=100...>; rel='last'`，可用于诊断，但**我们不发第二次请求**。

### 4.4 ★ 断点续传无效（入口和落地 URL 都无效）

对入口 URL：

```
curl -sL -r 0-1023        → 200, downloaded=101305834   （整包）
curl -sL -r 100000000-    → 200, downloaded=101305834   （整包）
```

对 302 之后的**最终 CDN URL**（`foruda.gitee.com/attach_file/{id}/{name}?token=...&ts=...`）复测：

```
step2  Range 0-1023 vs 落地 URL   → code=200 size=101305834
       响应头：Server: ADAS/1.0.214 / Content-Type: application/zip
               Content-Length: 101305834 / Cache-Control: max-age=2592000
               无 Accept-Ranges、无 Content-Range
step3  Range 100000000- vs 落地 URL → code=200 size=101305834
```

**结论：Gitee 的 CDN 完全不支持 Range，两级 URL 都不支持。** 源实现每次更新都会白跑一整趟全量请求（先带 Range 发一次 → 不是 206 → 删临时文件 → 再全量下一次）。

**设计决定：删掉断点续传**，只保留「上一次已经下完且校验通过的包直接复用」。慢网中断的代价由三件事兜：缓存复用、失败可重试、下载前把包大小显式告诉用户。

### 4.5 下载是两级 302 + 三个坑

```
https://gitee.com/{owner}/{repo}/releases/download/{tag}/{file}
  → 302 → https://gitee.com/{owner}/{repo}/attach_files/{id}/download/{file}
  → 302 → https://foruda.gitee.com/attach_file/{...}/{file}?token=...&ts=...&attname=...
  → 200
```

| 坑 | 事实 | 对策 |
|---|---|---|
| **落地 URL 是签名的时效 URL** | `token` 每次请求重新签发；`ts` 比请求时刻大 ≈29 天，与 `Cache-Control: max-age=2592000`（30 天）一致 | **绝不持久化落地 URL**，只存 `browser_download_url`，每次重新跟跳转 |
| **不存在的附件返回 HTML 错误页** | 404 + `Content-Type: text/html` + 6832 字节，`<title>你所访问的页面不存在 (404)</title>`；URL 里的 tag 段会被服务端校验 | **必须校验 HTTP 状态码**；只看「有内容」的下载器会把 HTML 存成 .zip |
| **Content-Type 不可信** | 实测 .zip 得到 `application/zip`、.exe 得到 `application/vnd.microsoft.portable-executable`；但官方 issue（`git-osc#IB93ZJ`，状态"已拒绝"）说"所有仓库下载都会返回 application/zip" | **一律不看 Content-Type**，只用 `Content-Length` + 自算 SHA-256 判定 |
| **`assets` 字段里不是附件** | `releases` 列表自带的 `assets` 装的是源码归档（`/archive/refs/tags/v1.6.0.zip`），URL 里 owner/repo 被小写化 | **附件必须另调 `/releases/{id}/attach_files`**（源实现走的就是这条路，正确） |

补充：无防盗链（无 Referer / 正确 Referer / 恶意 Referer 三种都成功，UA 变体一致）；**HEAD 可用**（200 + 正确 `Content-Length`）→ 可以在下载前预检。

### 4.6 ★★ 匿名限流：60 次、IP 绑定、403、20 分钟不恢复

| 事实 | 证据 |
|---|---|
| 匿名配额 `X-RateLimit-Limit: 60` | 响应头实测；跨仓库连续调用 `Remaining` 递减序列 `30 → 23 → 22 → 21 → 19 → 18 → 16` |
| **计数器与 IP 绑定**，同 IP 历史请求计入 | 首次探测就已剩 30，不是从 60 开始 |
| **耗尽返回 403，不是 429** | `HTTP/1.1 403 Forbidden` + `Content-Type: text/plain` + body 全文 35 字节：`403 Forbidden (Rate Limit Exceeded)` |
| 403 响应里**没有** `X-RateLimit-*` | 无法从失败响应读剩余量 |
| **恢复极慢** | 耗尽后每 20s 探测，`t+20`~`t+240s` 全部 403；隔 20+ 分钟再探测**仍是 403** |
| 403 有两种含义 | `openharmony/docs` 也返回 403（当时 Remaining≈16）→ 仓库级限制，**不能一律当限流** |
| 404 ≠ 无更新 | `RT-Thread/rt-thread` releases → 404（仓库不存在/无权访问）；`oschina/git-osc` 无 release → `[]` |
| 历史形态是 401 | Gitee 官方 issue（`git-osc#I3VUJD`，2021）里原文 `Unauthorized: Application has exceeded the rate limit`；官方口径「一个应用每天 1 万次」（指带 token），暗示匿名配额远低 |

**设计影响（这是本设计最容易被忽略、后果最重的一节）**：

1. **单次检查最多 2 个请求**：① `GET /releases?per_page=100` ② `GET /releases/{id}/attach_files?per_page=100`，**有更新时再加第三个下载清单**（清单也是附件，算一次下载请求，不占 API 配额的话另说，但按最坏情况算 3 次）。
   **绝不翻页、绝不并发、绝不重试风暴。**
2. **不做"最小检查间隔"节流**（v1.3 改定，你的答复 O2）：本地**仍然**持久化「上次检查时间」，但**只用于请求预算（手点 10 秒缓存）与日志，不用来拦任何一次检查**，界面上也不再显示它。剩下的天然节流只有两条：自动检查每次启动只做一次；用户手点「检查更新」走独立路径、10 秒内重复点击直接用缓存结果（2026-10-06 从 5 分钟缩到 10 秒，见 §7.3 第 3 条）。
3. **读 `X-RateLimit-Remaining`**：只**记账**（日志 + 界面显示"剩余配额 N 次"），**不用它拦任何一次检查**。
   ★ 2026-10-06 改动：原来"低于 10 就放弃本次检查并顺延"是个自动闸门，已在 §7.3 一并删除。
4. **失败语义必须分开**（这条直接决定用户看到什么文案）：

| 情况 | 判定 | 显示 |
|---|---|---|
| 403 + body 含 `Rate Limit Exceeded` | 限流 | 「Gitee 接口访问过于频繁，请稍后再试。」★ 2026-10-06 起**不再写退避时间、不再暂停自动检查**（原来写 `UpdateRateLimitUntil = 当天 24:00`，一次 403 就把当天自动检测整个关掉，见 §7.3） |
| 403 但 body 不是限流文案 | 仓库级拒绝 | 「Gitee 拒绝了对该仓库的访问。」 |
| 401 + `Application has exceeded the rate limit` | 历史形态限流 | 同限流处理 |
| 429 | 社区文档在传（实测是 403） | 兜底按限流处理 |
| 404 | 仓库不存在/无权访问 | 「找不到 Gitee 仓库或无权访问。」**不能显示成「已是最新版本」** |
| 网络异常/超时 | — | 连接失败文案，**不能显示成「已是最新版本」** |

5. **任何失败都绝不能显示为「当前已是最新版本」**（这是最容易犯、最误导用户的错）。
6. 检查是低频操作（启动一次 + 手动），**但"低频"不等于"无预算"**——60 次是**整个 IP 共享**的（同一台机器上其它工具、浏览器插件、其它仓库的调用都算）。所以必须按 60 规划，不能按"我一天只查一次"规划。

### 4.7 ★★ `prerelease` / `assets` 类型不可信（推翻 v1 的判断）

| 字段 | 官方 swagger 声明 | 实测 | 结论 |
|---|---|---|---|
| `prerelease` | **`string`** | JSON 布尔字面量 `false` → PowerShell 反序列化为 `System.Boolean` | **两种形态都要吃** |
| `assets` | **`string`** | `System.Object[]` | 同上 |
| `author` | `string` | Object | 同上 |

- 官方 swagger 的 Response Class **整块不可信**（`GET https://gitee.com/api/v5/swagger`；spec 不暴露 JSON/YAML，`/swagger.json` 等 404，只能读 HTML）。
- 官方帮助文档 UI 上是复选框（「这是一个预览版本」）→ 布尔语义才是正确的。
- **GitHub 的教训在这里以相反方向重演**：GitHub 是"文档说 bool、实际偶尔给 string"；Gitee 是"文档说 string、实际给 bool"。**结论一样：防御性解析。**
- ⚠️ **过滤逻辑不要写 `!prerelease`**：如果拿到字符串 `"false"`，它在 C# 里是真值，`!` 之后变 false → **正式版会被当成预发布版**，stable 通道永远挑不到包。
  → 统一走一个 `ReadBool(JsonElement)` 帮助方法：`True/False` 字面量直接取；字符串则 `bool.TryParse` 且同时接受 `"true"/"1"`；其它一律当 `false`。

**所以源项目那个 `JsonElement PrereleaseValue` + `[JsonIgnore] bool Prerelease` 的写法要保留下来**（v1 我判断它多余，是错的）。

### 4.8 ★ 容量上限（决定发布策略）

官方帮助文档 `https://help.gitee.com/repository/release/create` 原文：

> 「**单个附件不能超过 100M（GVP 项目 200M） 每个仓库总附件不可超过 1G（推荐项目不可超过 5G；GVP 项目不可超过 20G） 附件总容量统计包括仓库附件和发行版附件。**」

两个后果：

1. **单附件 ≤100MiB**：源项目那个包 101,305,834 字节 ≈ 96.6 MiB，**刚好卡在限制下面**。本工程的包更大（内置 CPython + Pillow），有超限风险 → **打包后必须先量体积**（§18-O3）。
2. **每仓库附件总量 ≤1GB**：假设一个更新包 100MB，**十来个 Release 就把仓库塞满**。所以：
   - 发布侧必须有「清理旧 Release 附件」的动作（附录 B）；
   - **这是否决「三个 RID 都发」的最硬理由**：3 个 RID × ~100MB = ~300MB/Release → **三个 Release 就爆**（§19）。

### 4.9 Gitee 的下载政策风险（备查）

官方 issue `git-osc#IB93ZJ`（2024-12，状态**已拒绝**）里 Gitee 回复：

> 「根据相关规定，gitee 无相关资质，无法提供 apk 安装包下载，望见谅」

→ **Gitee 会以「无资质」为由主动拦截某些文件类型的下载**，属不可预期政策风险。
**对策：只发 `.zip`，不发裸 `.exe`/`.apk`**（我们本来就是 zip，天然合规）。

| # | 场景 | 操作 | 结果 |
|---|---|---|---|
| A | 运行中的 exe | 改名 `app.exe → app.old.exe` | ✅ **成功** |
| A | 运行中的 exe | 删除（已改名腾位的）`app.old.exe` | ❌ 「对路径"…\A\app.old.exe"的访问被拒绝。」 |
| A | 运行中的 exe | 在原路径写入**新** `app.exe` | ✅ **成功**（腾位后落位可行） |
| A | 目录内有运行中的 exe | 整个目录改名 `A → A_moved` | ✅ **成功** |
| B | 有进程 **CWD** 在目录里 | 整个目录改名 | ❌ 「另一个进程正在使用此文件，因此该进程无法访问此文件。」 |
| B | 同上，杀掉该进程后 | 整个目录改名 | ✅ 成功 |
| C | `MoveFileExW(exe, exe.old, MOVEFILE_REPLACE_EXISTING=1)` | 替换**正在运行**的 exe | ✅ **返回 True (err=0)**，随后在原路径写新 exe 成功 |
| D | 目录内有被**独占打开**（`FileShare.None`）的文件 | 该文件改名 | ❌ 「另一个进程正在使用此文件…」 |
| D | 同上 | 整个目录改名 | ❌ 「访问被拒绝。」 |
| E | Velopack 式 `current` 目录切换 | 进程在跑时 `current → current.old` | ✅ 成功（新 `current` 落位、`current.old` 留作回滚） |
| F | 同进程内打开文件，`FileShare=` `Read` / `ReadWrite` / `None` | 该文件改名 | ❌ 全部失败 |
| F | 同进程内打开文件，`FileShare=ReadWrite\|Delete` | 该文件改名 | ✅ 成功 |
| F | 上述**任意** FileShare（含带 `Delete` 的） | 所在**目录**改名 | ❌ **全部失败** |
| G | 已加载的 .NET **托管**程序集（`Assembly.LoadFrom`） | `MoveFileEx` 改名 / 删除 / 覆盖 / 所在目录改名 | ✅ 全部成功（`LoadFrom` 读完字节即关句柄） |
| H | 进程 **CWD** 停在安装目录（updater 的典型反例） | 整个目录改名 | ❌ **失败** |

★★ **四条可复现规则**（写代码时按这四条走）：

1. **运行中的原生映像（`.exe`/`.dll`）**：**能改名、不能删、腾位后能在原路径写新文件** —— 这正是微软官方 `Dynamic-Link 库更新` 文档推荐的替换法（`MoveFileEx` 改名腾位 → 写新文件）。
2. **目录内只要有任何一个未关闭的文件句柄，目录就不能改名**（根因：句柄 pin 住了父目录对象）。
3. **进程 CWD 在目录里 → 目录不能改名**（第 2 条的变体：CWD 本身就是一个目录句柄）。
4. **单个文件能否改名**，取决于打开它的句柄是否允许 delete 共享（`FileShare.Delete`）。

**被实测修正的三条常见说法**：

- ❌ Velopack 文档「目录里有文件在用（a process running inside `current`）就不能改名」→ **在本机不成立**：运行中的 exe 映像**不**阻止目录改名（实验 A / E）。
- ✅ 但 Velopack 点名的另外两条**成立且致命**：**CWD 在目录里的进程**、**杀软 / Windows Defender**（实验 B / H）。
- ⚠️ 「托管程序集能随便覆盖」**不能推广到原生 dll**：`Assembly.LoadFrom` 关句柄是托管加载器的行为；原生 dll 走 image section 映射，行为是实验 A 那套（**能改名、不能删**）。

**这三条结论直接定了三件事**：

1. §9.3 的 `WorkingDirectory` **绝不能**是安装目录（实验 H）；
2. §9.6 用「**两阶段原地替换**」（先整批 `MoveFileEx` 腾位，再整批落位），**而不是**"先删后写"（正在运行的 exe 根本删不掉）；
3. **不**采用 Velopack 的「stub + `current` 目录整体切换」布局 —— 逐条理由见 §9.6。

### 5.2 为什么这样拆（v1.2 按「能分开就分开」细化）

- **纯逻辑单独一类，且不许碰 IO**：`UpdateVersion`（版本比较边界）、`UpdateChannelSelector`（通道挑选）、`UpdateApplyPlan`（白名单 + 动作集合）、`UpdatePackageValidator`（zip-slip / 包内清单）、`UpdateRequestBudget`（§7.3 六条规则）全部是**输入 → 输出**的纯函数 → 回归测试可以直接喂数据断言，**不必扫源码、不必联网、不必造临时目录**（棘轮 ⑤ 的关键，§15）。
- **`GiteeReleaseClient` 是唯一碰网络的地方** → 配额记账、状态码语义（403 限流 vs 403 拒绝 vs 404）、防御性 JSON 解析全集中在一处，出问题一眼定位。
- **磁盘那几件事各自一个文件**（下载 / 缓存 / 清理）→ 单独可测，且"清理"这种容易被忘掉的收尾有自己的家。
- **`UpdateService` 只剩编排**，读一遍就能看懂整条链路。
- **`UpdateLaunchService` 只做「起进程 + 等文件」**，没有 UI 依赖 → 好测。
- **单个文件小**，评审和护栏都轻松；`Services/**/*.cs` 的棘轮上限是 1049 行，本设计每个文件都远小于它。

## 6. 数据契约（三个 JSON）

### 6.1 `toolbox-update.json` —— Release 附件中的更新清单

```jsonc
{
  "schemaVersion": 1,
  "toolboxStableKey": "GalExcleTools",       // ASCII！用于路径与一致性校验
  "displayName": "TFAC剧情箱-轮椅版",              // 全角冒号没问题，只用于界面显示
  "version": "1.0.1",                             // 语义化版本，可带 -Beta / -Beta.2
  "channel": "stable",                            // "stable" | "beta"
  "publishedAt": "2026-10-02T12:00:00+08:00",

  "releaseNotesUrl": "https://gitee.com/xiaojie578/TFACStorybox/releases/tag/v1.0.1",
  "releaseNotes": "本次更新内容……",
  "requiresManualMigration": false,               // true → 提示「需要手动更新」并给 Release 页
  "requiresRestart": true,
  "assets": [
    { "runtime": "win-x64", "fileName": "GalExcleTools-v1.0.1-win-x64.zip",
      "sha256": "……64 位小写十六进制……", "sizeBytes": 123456789, "downloadUrl": "" }
  ]
}
```

★ **分卷（2026-10-06 增补，见 `Docs\热更新-分卷与双通道-契约.md`）**：整包超过 Gitee 单附件 100 MiB 时，
发布侧把**同一个 zip** 按字节切成若干 `…partNN.zip`，清单里的 `assets[]` 多一个可选字段：

```jsonc
    { "runtime": "win-x64", "fileName": "GalExcleTools-v1.0.1-win-x64.zip",  // ← 仍是**整包**名
      "sha256": "……整包的哈希……", "sizeBytes": 123456789, "downloadUrl": "",
      "parts": [                                                                   // ← 只在分卷时存在
        { "fileName": "GalExcleTools-v1.0.1-win-x64.part01.zip", "sha256": "……第 1 卷自己的……", "sizeBytes": 99614720 },
        { "fileName": "GalExcleTools-v1.0.1-win-x64.part02.zip", "sha256": "……第 2 卷自己的……", "sizeBytes": 41378269 }
      ] }
```

四条铁律（写错任何一条都会把用户更新到半个程序上）：

1. `assets[].fileName / sha256 / sizeBytes` **永远是拼接后整包**的语义 —— 不是任何一卷的；
2. `parts[]` 是**可选**字段，必须按「可能不存在」解析（不分卷时它就不在清单里）；
3. `parts[].sha256 / sizeBytes` 是**该卷自己**的，逐卷校验收尾用；
4. `parts[].downloadUrl` 由客户端填（和整包一样，拿 `fileName` 去 attach_files 按名匹配），
   而分卷时**整包本身不作为附件上传**，所以整包的 `downloadUrl` 会一直是空串 —— 这不是错误。
   另外「是否分卷」只以 `parts[]` 为准，**不要**去数 `….sha256.txt` 的行数（那是给人看的台账）。

客户端的处理（对齐源实现 `FillReleaseInfo`）：
- `assets[].downloadUrl` 为空是**正常的** —— 真实下载地址由客户端拿 `fileName` 去 **attach_files** 列表里按名字匹配后填上（Gitee 的附件 URL 必须从 API 拿，不能猜，见 §4.5）。
- `releaseNotes` 为空 → 显示「本次 Release 没有填写更新公告。」
- 匹配 `fileName` 时用 `OrdinalIgnoreCase`（附件名大小写在不同打包器下可能变化）。
- ~~`minSupportedVersion`~~ **已在 2026-10-06 删除**（清单结构、发布脚本、客户端三处一起）：它是个反直觉的闸门 ——
  一个自动推导出来的版本号就能把所有人的自动升级关死（v2.0.3 被算成 2.0.2、v2.0.4 被算成 2.0.3，两次都踩到）。
  原则改为**旧版兼容**：新版本自己负责让老客户端吃得下去。

### 6.2 `update-package.json` —— **zip 包内**的包体检单

```jsonc
{
  "schemaVersion": 1,
  "toolboxStableKey": "GalExcleTools",
  "version": "1.0.1",
  "runtime": "win-x64",
  "entryExe": "TFAC剧情箱-轮椅版.exe",
  "windowsAppSdkRuntime": "2.0",               // 框架依赖才有值；自包含为空串（见 §9.10）
  "createdAt": "2026-10-02T12:00:00+08:00"
}
```

updater 的匹配规则（沿用源实现，逐条都要）：
1. 递归找 `update-package.json`；
2. `toolboxStableKey` 必须等于本次运行的 key；
3. `version` 必须等于目标版本；
4. 同目录下必须存在 `entryExe` 指名的文件；
5. 找不到 → 抛错并把**所有候选清单**打进错误信息（排查全靠这个）；
6. `windowsAppSdkRuntime` 非空 ⇒ 覆盖前必须先确认运行时在位（§9.10），否则**中止更新**。

### 6.3 `settings.json` 新增字段（全部要有默认值）

现有 `settings.json` 没有这些 key → 反序列化后落到默认值。**没有任何版本化迁移逻辑**（`AppSettingsService` 里没有 `Version` 字段），所以默认值就是唯一的行为开关。

|---|---|---|---|

| `UpdateAutoCheckEnabled` | bool | **`true`** | 关掉 = **启动时也不自动检查**（手动按钮仍可用）。v1.3：定时器已整体删除，「自动检查」只剩"启动查一次"这一种形态，所以**不再需要第二个开关** |
| `UpdateCheckOnStartup` | bool | ~~`true`~~ | **v1.3 已删除**（与 `UpdateAutoCheckEnabled` 语义重合，合并成一个） |

### 6.4 本地状态文件 `update-state.json`（v1.4 新增：**状态与「计划」分开持久化**）

借鉴 Android 端 `UpdateStateStore.java:22-55` + `LauncherUpdateService.java:44-47`：**状态和"计划（plan）"必须分开存**。只存一个 `status` 字符串的话，重启后无法判断"这个 ready 是哪一个版本的"，也无法判断"已经下好的那个包还算不算数"。绿色版没有系统安装器回调，重启后只能靠盘上状态自己恢复。

路径：`%LOCALAPPDATA%\GalExcleTools\update-state.json`（**不放安装目录**，与 settings 同思路，免得覆盖时被一起换掉）。

```jsonc
{
  "schemaVersion": 1,
  "status": "idle",              // idle | downloading | ready | applying | error
  "targetVersion": "1.0.2",      // 这个状态属于哪个版本 ★ 关键字段
  "package": {                   // ← 这就是"plan"，单独存才能自校验
    "fileName": "GalExcleTools-v1.0.2-win-x64.zip",
    "sha256": "…", "sizeBytes": 12345678, "runtime": "win-x64"
  },
  "updatedAt": "2026-10-05T12:00:00+08:00",
  "message": null
}
```

规则：

- **写入必须原子**（本工程已有 `AtomicFileWriter`）：先写 `.tmp` 再替换。状态文件写坏比没有状态更糟 —— Android 端为此专门有一条文案「启动器更新状态已损坏，请重新下载。」。
- **启动自检**：`status=="ready"` 时按 `targetVersion` 与当前运行版本比较 ——
  - 相等 → 更新已经装上了 → 丢弃状态 + 删包；
  - 更高 → 保留，界面显示「已下载 1.0.2，可直接更新」；
  - 更低 → 丢弃（**永不降级**，见 §20.4 的第一条教训）。
- `status=="downloading"` 但这次是**新起的进程** → 上次被杀了 → 改判 `error` +「更新下载曾被中断，请重新开始。」（对应 Android `AndroidLauncherPlugin.java:455-458`）。
- 这个文件**只由客户端读写**；updater 绝不碰它（updater 的契约只有参数 + `READY` 文件 + 退出码，见 §9.1）。

## 7. 检查更新流程

### 7.1 通道与版本选择规则

```csharp
public enum UpdateChannel { Stable, Beta }
```

```
触发时机与请求预算检查（§7.3）：应用启动后延时 5 秒触发**一次**（无定时器/轮询）；
          ★ 启动这一路查到可装更新就直接弹「发现新版本」确认框（2026-10-06 起，对齐源实现的
          `allowUpdatePrompt: true`）：启动路径不显示进度框，但确认之后走的是和手点按钮
          **完全同一条**下载 → 校验 → 覆盖路线；点「继续使用旧版」就什么都不做；
          或用户手点
拉列表： GET {GiteeReleaseApiUrl}?per_page=100          ← 必须带（§4.3）
        └ 读 X-RateLimit-Remaining；<10 → 放弃本次并顺延（§4.6）
挑一条：
  Stable : 取 prerelease == false 的，按版本降序，平手再比 created_at 降序 → 第一条
  Beta   : 取全部（含正式版）按版本降序，平手时正式版优先（ThenBy(prerelease)），
           再比 created_at 降序 → 第一条
取附件： GET {GiteeReleaseApiUrl}/{release.id}/attach_files?per_page=100
下载清单：在附件里找 name == "toolbox-update.json"（OrdinalIgnoreCase）→ 下载 → 反序列化
          → 用 fileName 匹配填 assets[].downloadUrl
          → releaseNotes / releaseNotesUrl 为空时用 Release 的 body / html_url 兜底
比版本： CompareSemantic(newVersion, currentVersion) > 0 → 有更新
```

**版本语义**（照搬源实现，边界正确）：
- 先比 `Major.Minor.Patch.Build`；
- 正式版 > 预发布版（`1.0.0` > `1.0.0-Beta`）；
- 都是预发布 → 标签按 `.` 切段逐段比：数字段按整数比，**数字段 < 非数字段**，其余按 `OrdinalIgnoreCase` 字符串比；
- 解析时先 `TrimStart('v','V')`，截到 `+` 之前、`-` 之前。

### 7.2 各种结果的处理（文案也是契约的一部分）

| 情况 | 结果 |
|---|---|
| 列表为空 / 通道内没有 Release | 「Gitee 上没有找到可用的 Release。」+ Release 页地址 |
| 有 Release 但没有 `toolbox-update.json` 附件 | 「发现 {tag}，但该 Release 没有更新清单，请手动下载。」 |
| 清单里没有匹配 `runtime` 的包 | 「发现 {ver}，但没有 win-x64 更新包。」 |
| `requiresManualMigration == true` | 「发现 {ver}，但该版本需要手动更新。」 |

| 附件里找不到整包名 / 某卷名（分卷） | 「清单里的 {fileName} 在 Release 附件里找不到，请手动下载。」/「发现 {ver}，但更新包分卷 {part} 不在 Release 附件里，请手动下载。」 |
| 新版本 ≤ 当前版本 | stable 通道且当前是预发布版 → 「当前测试版 V{cur} 比正式版 V{latest} 更新；如果要用正式版，请自行去 Gitee 下载。」；否则「当前已是最新版本：{cur}」 |
| 超时 | `TimeoutException`：「Gitee 连接超时（{n} 秒）。请检查网络或稍后重试。」 |
| 限流（403/401/429 + 限流文案） | 「Gitee 接口访问过于频繁，请稍后再试。」（不写退避时间、不暂停自动检查） |
| 403（非限流文案） | 「Gitee 拒绝了对该仓库的访问。」 |
| 404 | 「找不到 Gitee 仓库或无权访问。」 |
| 取消 | 不算失败：「检查已取消」/「没有下载或替换任何文件。」 |
| **以上任何失败** | **绝不能显示为「已是最新版本」** |

### 7.3 请求预算（本设计的核心安全阀）

```
**触发时机（v1.2 按你的答复改定）**：

| 触发源 | 时机 | 频率 |
|---|---|---|
| 自动 | 应用启动、主窗口首次渲染完成后**延时 5 秒** | **每次启动最多 1 次；没有任何定时器 / 轮询**；查到可装更新就用「发现新版本」确认框告诉用户（2026-10-06 起） |
| 手动 | 用户点设置页「检查更新」按钮 | 随时（但受下面第 3 条的缓存约束） |

> 你的原话：「自动更新只在启动的时候会触发，不用一直检测。」
> 所以设计里**不再有任何 `Timer` / `PeriodicTimer` / `while(true) + Delay`**；启动时那一次由 `MainWindow.xaml.cs` 构造末尾的 `_ = CheckUpdateOnStartupAsync();` 发起（§10.2）。

**规则**：

```
1. 单次检查的 API 请求数 ≤ 2（列表 + 附件）；下载清单/包走下载通道，不算 API 配额但也别浪费
2. 自动检查每次启动只做一次，**没有任何节流开关**（v1.3：UpdateThrottleSameDayCheck 已按
   你的答复 O2 整条删掉）→ 语义就是纯粹的"启动就查"，由 UpdateAutoCheckEnabled 一个开关控制
   ⚠️ 因此请求预算（本节）是唯一防线：匿名配额只有 60 且按 IP 计（§4.6）。用户一天开 20 次
     工具就是 20 次列表请求，再叠加同一 IP 上的其它人，很容易撞 403（登记为 §17-R13）。
     发布前实测一轮真实配额消耗；真出问题时的补救顺序是：先加"启动检查最短间隔"，
     再考虑给检查请求带 token（带 token 的配额是每天 1w 次）。
3. 用户手点「检查更新」：无视第 2 条，但 **10 秒内**重复点击直接用缓存（2026-10-06 从 5 分钟改：
   启动检查刚跑完再手点，5 分钟窗口会让界面一直显示同一份旧结论，看着像"点了没反应"；缩到
   10 秒只挡"手一抖点两下"，真想重查就真去问 Gitee —— 匿名配额 60 次/小时，手点几次不成问题）
4. 任一次响应里 X-RateLimit-Remaining 只**记账**（日志 + 界面"剩余配额"），**不用来拦检查**
5. ★ 2026-10-06 删除：原来的「配额低于 10 就收手」「限流后退避到当天 24:00」「退避期内自动检查静默跳过」
   三条**整套删除**（连同 settings.json 里的 `UpdateRateLimitUntil` 字段）。失败就是这一次失败，
   下一次启动/手点照常检查 —— 与 FantasyTools 一致。理由见本节末尾。
6. 绝不并发、绝不翻页、绝不因为失败而立刻重试；一次检查里"列表 + 附件"两个请求也不并存
```

> ★ **2026-10-06 定案：删掉"限流自锁"**（用户实测踩到：客户端显示「已暂停自动检查（2026-10-07 00:00 之后恢复）」，
> 一次 403 换来一整天的自动检测失效，而且是写进 settings.json 的，重开程序也还在跳过）。
> 参照实现是 FantasyTools —— 它**没有任何** `RateLimitUntil` / 退避记录 / 跳过逻辑：失败就是这一次失败。
> 教训与另一处同源（见 §21.5 第 19 条）：**凡是"自动推出来的闸门"都要先问一句 —— 它算错时会不会把整条路关死？**
> 现在的形状：单次检查 ≤2 个请求 + 手点 10 秒缓存 + 失败语义分清；**不做任何跨小时的自我封锁**。

**注意 403 的两种含义**（§4.6 实测）：Gitee 耗尽配额返回的是 **HTTP 403 + `Content-Type: text/plain` + body 全文 35 字节 `403 Forbidden (Rate Limit Exceeded)`**，**不是 429**。但 403 也可能是"无权访问"（实测 `openharmony/docs` 在 `X-RateLimit-Remaining` 还有 16 时就返回 403）→ **必须同时看 body 文案**才能区分，不能一律当限流（§7.2 已把两种分开定义）。
```

### 7.4 超时与取消

- `HttpClient`：单例，`Timeout = Timeout.InfiniteTimeSpan`，`UserAgent = "GalExcleTools-Updater/1.0"`。
- 每个网络操作用 `CancellationTokenSource(TimeSpan.FromSeconds(clamp(设置值,10,600)))` + `CreateLinkedTokenSource(用户取消)`。
- 用户取消来源 = `MainWindow.Progress.cs:78 GetGlobalProgressCancellationToken()`。
  ⚠️ **只有走 `ShowGlobalProgress` 打开进度条时这个 token 才有意义**。启动时的静默检查不显示进度条 → 传 `CancellationToken.None`（源项目就是这么分的）。手动检查和下载必须显示进度条。
- **下载阶段不要用 120 秒的连接超时**：那是"连接/响应"超时。下载用「无总时长上限 + 用户可取消」，只在「连续 30 秒没有收到任何字节」时判超时（读循环里的看门狗）。

## 8. 下载与校验流程

### 8.1 步骤（进度号沿用源实现量级，写死在代码里并注释）

```
包路径：%LOCALAPPDATA%\GalExcleTools\Updates\{fileName}
临时名：{packagePath}.download

⓪ 多实例预检（§9.7）——放在最前面，别等下完 100MB 才发现装不上
① 复用：若 packagePath 已存在 → 校验 size → 校验 SHA-256 → 校验包结构
        全过 → 100%「已复用缓存更新包。」直接进 §9
        任一不过 → 删掉它，重新下
② 清理：删掉同目录下所有 *.download（上次失败留下的）
③④ 逐「载荷」下载（载荷 = 分卷时是**每一卷**，否则就是整包自己，见 §6.1）：
     对每个载荷：
      ③ HEAD 预检：对 browser_download_url 发 HEAD（跟随 302）
            → 状态码 != 200 → 抛错（404 会是 HTML 错误页，见 §4.5）
            → Content-Length != 该载荷的 sizeBytes → 抛「远端包大小与清单不一致（第 N/M 卷）」
      ④ GET（自动跟 302）→ **追加写**入同一个 .download
            （FileMode.OpenOrCreate + SetLength(已完成的长度) + Position：重试只截掉本卷尾巴，
              前几卷已经校验过的字节一个都不动）
            缓冲 128KB；进度 8% → 70%，总量按**整包**算（用户看到的是一个包）
            文案：「正在下载更新包（第 N/M 卷）...」+ "已下 / 总量"；只有一卷时不加卷后缀
            边写边用 IncrementalHash 算**这一卷**的 SHA-256
         该卷下完立刻校验：大小 → 卷 SHA-256（不等 → 删掉重下该卷；仍失败 → 整次失败）
            ★ 坏卷当场失败：后面的卷一个都不去下（不白花用户的流量）
        ★ 进度**节流 350ms 一次**（借鉴 Android 端 `LauncherUpdateDownloader.java:42`）：
          否则 100MB 包会刷出上千次 UI 更新、把日志也写爆
        ★ 失败重试**最多 3 次**，间隔 `500ms × 第几次`（借鉴 Android `LauncherUpdateService.java:158-173`）；
          重试期间文案「连接中断，正在重试 N / 3」；**用户取消不重试**；
          已收到响应体的校验类失败（大小/哈希不符）**不重试**，直接删包重下
        看门狗：连续 30 秒零字节 → 抛 TimeoutException
⑤ 大小：72%「正在校验更新包大小...」→ 比的是**拼接后的总字节数** vs 声明值 → 不等则删 .download 并抛
        「更新包大小校验失败：{实际} / {期望}」
⑥ magic：读头 4 字节必须是 50 4B 03 04（zip）→ 不是则删并抛
        「下载到的不是有效的 zip 文件（可能是错误页）。」
⑦ SHA ：82%「正在校验 SHA-256...」→ 重读**整个文件**算哈希，与 `assets[].sha256` 比 → 不等则删 .download 并抛
        「更新包 SHA-256 不一致：{实际}」
⑧ 结构：92%「正在校验更新包结构...」→ ZipFile.OpenRead 逐项检查（§6.2）
⑨ 落地：File.Move(.download → packagePath) → 100%「更新包已准备就绪。」
⑩ 清理：删掉非本次的 *.download；包文件只保留最近 2 个（按 LastWriteTimeUtc 降序）
```

**分卷的两道校验缺一不可**（§6.1 的铁律③④）：逐卷 SHA-256 挡「哪一卷坏了」，
拼完之后对整包再算一次 SHA-256 挡「卷的顺序错了 / 边界错了」——
后者是逐卷校验**永远**发现不了的（每一卷都完好，拼起来却是另一个文件）。
任何一卷失败 = 整次失败，**绝不允许留下「拼了一半」的 `.download` 当成品**：
它一旦被当成「下好的包」复用，覆盖上去就是半个程序。同理，缓存复用（①）只认**已经整体校验通过**的包名，
「卷下齐但没拼」「拼完没校验」都不算。

**为什么必须先下到 `.download` 再改名**：直接下到正式文件名的话，下次运行会看到一个大小/哈希不符的半截包。改名是原子的（同分区 `File.Move`），所以「正式文件名存在 ⇒ 一定是一个完整的包」。

> 下载产物不经过 `AtomicFileWriter`（那是给小 JSON/文本用的），但**原子改名的语义必须保持**，这是同一条规矩的等价做法。

### 8.2 结构校验（`ValidatePackage`）

```csharp
using var archive = ZipFile.OpenRead(packagePath);
// 1) 必须存在名为 update-package.json 的条目    否则「更新包缺少 update-package.json。」
// 2) 反序列化失败                              →「update-package.json 无法读取。」
// 3) toolboxStableKey 不等                     →「更新包工具箱标识不匹配。」
// 4) version 不等                              →「更新包版本和清单版本不一致。」
// 5) runtime 不等                              →「更新包 Runtime 不匹配。」
// 6) 没有任何条目的文件名 == EntryExe           →「更新包缺少主程序 exe。」
// 7) ★ 该条目的解压后长度 <= 0                  →「更新包里的主程序 exe 是空文件。」
//    （借鉴 Android 的第三层「包身份」校验：大小 → SHA-256 → **包身份**，
//      见 `LauncherUpdateService.java:176-188`。Android 查的是包名/versionCode/签名，

```

⚠️ 第 6 条要和 `热更新覆盖.ps1` 的 `Resolve-PackageSourceRoot` 保持一致：**双方都按「条目文件名 == entryExe」判断**，不要一边用全路径一边用文件名。
⚠️ 条目名里的分隔符可能是 `\` 也可能是 `/`（实测：PowerShell `Compress-Archive` 与 .NET 写 `\`，**Bandizip 写 `/`**）→ 比较文件名时**先 `Replace('/', '\\')` 归一化**。

### 9.3 ★ 为什么不用 `cmd.exe` 中转

源实现生成 `RunUpdate-*.cmd`（内容带 `chcp 65001`）再 `cmd.exe /c` 启动。在本工程会踩两个雷：

1. **exe 名含全角冒号**：`TFAC剧情箱-轮椅版.exe`。`cmd.exe` 读 `.cmd` 文件的时机早于 `chcp 65001` 生效，非 ASCII 字符的解析结果不可预期（同一份文件在不同区域设置/codepage 下表现不同）。
2. **安装路径可能带中文**（`D:\本工具\…`），拼进命令行后引号 + 编码双重风险。

**改为直接用 `ArgumentList` 起 PowerShell**：

```csharp
var psi = new ProcessStartInfo
{
    FileName  = powershellPath,             // Windows PowerShell 5.1（系统自带，不依赖 pwsh）
    UseShellExecute = false,                // ArgumentList 要求 false
    CreateNoWindow  = false,                // 要用户看得见这个窗口
    WorkingDirectory = updaterWorkDir,      // ★★ 绝不能是 AppContext.BaseDirectory！见下
    WindowStyle = ProcessWindowStyle.Normal
};
psi.ArgumentList.Add("-NoProfile");
psi.ArgumentList.Add("-ExecutionPolicy"); psi.ArgumentList.Add("Bypass");
psi.ArgumentList.Add("-File");            psi.ArgumentList.Add(updaterPath);
psi.ArgumentList.Add("-AppProcessId");    psi.ArgumentList.Add(pid.ToString());
psi.ArgumentList.Add("-InstallDir");      psi.ArgumentList.Add(AppContext.BaseDirectory);
/* …其余参数同理，一个参数一个 Add… */
Process.Start(psi);
```

- **无 shell** → 没有引号转义、没有 codepage 问题；中文路径/文件名在 `ArgumentList` 里是独立的 UTF-16 字符串，交给 `CreateProcessW`。
- 窗口仍然可见（`powershell.exe` 是控制台程序，`CreateNoWindow=false` 会新建控制台窗口）。
- **失败时窗口不会闪退**：由 `.ps1` 自己 `[void][System.Console]::ReadLine()` 兜住（**成功和失败两条路径都要有**），所以不再需要 `.cmd` 里那套 `pause`。
- 代价：`cmd` 里的 `where powershell.exe` 自检没了 → 改成在 C# 侧先探测 `powershell.exe` 是否存在，找不到就直接报「系统里没有找到 PowerShell，无法完成热更新。」，**不要启动一个必然失败的进程**。

> ★★ **`WorkingDirectory` 必须是一个与安装目录无关的空目录**（建议 `%LOCALAPPDATA%\GalExcleTools\UpdateRunners\`）。
> **依据是本机实测**（§4.10 实验 H）：只要有一个进程的 CWD 停在安装目录里，**整个安装目录就无法改名**（`Rename-Item` 报「另一个进程正在使用此文件，因此该进程无法访问此文件。」）。v1.1 把 `WorkingDirectory` 写成 `AppContext.BaseDirectory`，等于让 updater 主动把安装目录钉死 —— 一旦以后要做"整目录改名"式的原子切换，或者 Windows / 杀软对某个子文件做目录级操作，就会当场失败，而且**没有任何报错会指向 CWD 这个原因**。
>
> 同理，**updater 脚本自身也要放在安装目录之外**：客户端启动前把 `热更新覆盖.ps1` 从安装目录**复制到** `%LOCALAPPDATA%\GalExcleTools\UpdateRunners\`，再从那里启动。这样 updater 运行期间**不持有安装目录内的任何句柄**，完全不参与"谁锁着安装目录"这件事。

> ⚠️ **不要用 `Start-Process -Wait`**（社区实测有两类挂起：配 `-Verb RunAs` 时不等、配 `-NoNewWindow` 时可能永久挂住）。等进程退出一律用 `$p = Get-Process -Id …; $p.WaitForExit(30000)`。
> ⚠️ **不要自己提权**（`-Verb RunAs`）。UAC 提权只能走 ShellExecute，`-Wait` 不可靠且拿不到输出。本工程装在 `D:\DabaoV\…`（非受保护目录），正常免提权；**万一写失败，按"先非提权尝试、失败后再询问用户"处理，不静默弹 UAC**。

> 保险丝：若实测发现 `ArgumentList` 这条路在 WinUI 宿主里有意外（窗口不出现 / 退出码拿不到），退路是「`.cmd` 全 ASCII + 中文参数改走一个 UTF-8 的 JSON 参数文件」（§17-R2）。

### 9.4 ★ 解压：不要用 `Expand-Archive`

本包内含 `Tools/Atlas/python/`（CPython 3.13 + Pillow 全套，数千个小文件）。社区实测 `Expand-Archive` 在这种结构上"慢得要死"（它逐条走 PowerShell 管道）。

**用 .NET 的 `ZipFile.ExtractToDirectory`**（本机实测中文名正确还原）：

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
# 解压前先自己扫一遍条目名，做 zip-slip 校验
$zip = [System.IO.Compression.ZipFile]::OpenRead($PackagePath)
foreach ($e in $zip.Entries) {
    $n = $e.FullName.Replace('/','\')
    if ($n -match '(^|\\)\.\.(\\|$)' -or $n -match '^[A-Za-z]:' -or $n.StartsWith('\')) {
        throw "更新包内含有非法路径条目：$($e.FullName)"
    }
}
$zip.Dispose()
[System.IO.Compression.ZipFile]::ExtractToDirectory($PackagePath, $stagingRoot, $true)
```

**为什么必须自己扫条目**：PowerShell 5.1 跑在 .NET Framework 上，**.NET Framework 的 `ExtractToDirectory` 不做 zip-slip 路径校验**（.NET Core 2.1+ 才加）。信任链其实已经靠 SHA-256 建立了，但这几行是廉价的二道防线。
（备选：`tar.exe -xf`，Windows 10 1803+ 自带，本机实测存在且中文名正确。）

**zip 中文文件名的实测结论（本机，2026-10-02）**：

| 打包器 | 中文条目名 | UTF-8 flag (0x800) | `.NET ExtractToDirectory` | `tar.exe -xf` |
|---|---|---|---|---|
| PowerShell 5.1 `Compress-Archive` | `TFAC剧情箱-轮椅版.txt` ✅ | **未设置** | 正确 | 正确 |
| Bandizip `bz.exe` | 同上 ✅（目录条目用 `/`） | **未设置** | 正确 | 正确 |
| .NET `ZipFile.CreateFromDirectory` | 同上 ✅ | **未设置** | 正确 | 正确 |

- 三种打包器都**没有**设置 UTF-8 flag → 非 ASCII 名靠"当前 ANSI 代码页"往返。**中文 Windows 上实测无损**，但换到非中文 Windows 理论上会乱码。用户群是中文 Windows，风险可接受；**如果以后要收紧，就得在打包侧强制写 UTF-8 flag**（Bandizip 的 CLI 参数需实测，`Compress-Archive` 没这个开关）。
- **目录条目里可能有 `/` 也有 `\`** → 所有名字比较都要先归一化（§8.2）。
- Bandizip 会额外写入目录条目（`Assets/`），无害。

### 9.5 不做整目录备份（v1.3 定案）+ 零成本替代：「延迟一轮清理」的回滚窗口

**决策：不做覆盖前的整目录备份**（你的答复 O3「不需要」）。理由你自己说得比我准：

> 「我做的 winui 工具都有一个专门的工作区，和软件没有硬关联。」

也就是说安装目录里**全是可再生的程序文件**（`TFAC剧情箱-轮椅版.exe` + 一堆 dll + WASDK 原生件 + `.pri`/`.xbf` + 内置 Python），没有"丢了就找不回来"的东西 —— 用户数据本来就不在安装目录里（`settings.json` 在 `%AppData%`、`runtime.log` 在 `%LocalAppData%`、工程数据在用户自选的工作区，§3.4 已逐条核实）。花一个包的量级去备份一个"重下即得"的目录，不值。

**但"更新成功、新版起不来"这条路必须留一个出口**，否则 §9.8 的杀软风险就无处兜底。用两阶段替换天然产生的东西解决，**零额外成本**：

```
两阶段替换（§9.6）会把每个被替换 / 被删除的旧文件原地改名成
        TFAC剧情箱-轮椅版.exe.old-1.0.0
        ZDTool.Core.dll.old-1.0.0
        ...

  阶段 2 失败  → 立刻逆序回滚（§9.6），当场恢复成更新前的样子
  阶段 2 成功  → ★ 不要马上删！

★ 延迟一轮清理（v1.3 新增，替代原来的备份）：
   新版启动成功的判定点：写一份"启动成功标记"到 %LOCALAPPDATA%\GalExcleTools\
   （内容：版本号 + 时间戳 + 本次 TargetVersion）
   下一次启动（此时"新版能跑起来"已经被真实验证过一次）才清理上一轮的 *.old-{ver}
   → 也就是说 *.old-{ver} 在盘上至少存活「一次启动 + 一次关闭」的时间
```

> **实施口径（M5 落地时钉死的细节）**：清理只认「启动标记里的版本 == 现在跑的这个版本」这一种证据，
> 而且这一版得**连着启动第二次**才轮得到清理 —— 升级到 1.0.1 的那一次启动写下标记（1.0.1），
> 用户第二次启动 1.0.1 时才清 `*.old-1.0.1`。中间只要换过版本（比如用户把旧版改回来跑了一次），
> 证据就作废、回滚文件继续留着 —— 宁可多留一轮，方向是安全的。
> updater 删不掉的回滚文件清单 `PendingCleanup.txt` 同样只在这一刻才去删（删不掉的继续留在清单里）。

于是三种失败形态都有确定性出路：

| 失败形态 | 出路 |
|---|---|
| 阶段 2 中途失败 / 断电 / updater 被杀 | updater 当场逆序回滚（§9.6）；即使没来得及回滚，`*.old-{ver}` 也都在原地 → 下次启动提示手工改回原名 |
| **更新成功但新版起不来**（杀软拦截 / WASDK 装载失败） | `*.old-{ver}` **还没被清理**（"启动成功标记"从未写出）→ 把后缀去掉即可完整退回更新前，旧 exe 双击就能用 |
| 新版用了一阵才发现某功能坏了 | 本地已无旧文件 → **重新下载上一版 Release 包**（见下面的发布侧硬要求） |

- **代价**：被替换的那批文件会**多占一轮**的磁盘（新旧同时在盘上）。但这是两阶段替换**本来就需要的空间**，不是新增开销（§14 磁盘预检按 ×3 估算的正是"包 + staging + 一轮旧文件"）。
- **不做的事**：不写 `UpdateBackup\` 目录、不做 robocopy、不需要 `UpdateKeepBackup` 设置字段（§6.3 已删）。
- **恢复指引的措辞跟着改**：不再是"去备份目录拷回来"，而是「把程序目录里的 `*.old-版本号` 文件改名回原名（去掉 `.old-…` 后缀）即可回到更新前」。
- ⚠️ **明确记下来的缺口**：这条兜底只在"旧文件还在"时有效；一旦下一轮启动的清理跑过，退路只剩**重新下载上一版 Release 包**。由此形成一条**发布侧硬要求**：

> **Release 里至少保留最近 2~3 个版本的包附件**（`GalExcleTools-v1.0.2-win-x64.zip` 等）。
> 这与 §4.8 的「每仓库附件总量 ≤ 1GB」直接冲突 —— 单包若接近 100MiB 就只能留 1~2 个版本。
> 出包侧（附录 B，本轮不做）必须先量真实包体积，再定"留几个版本 + 要不要分包 / 增量"。

### 9.6 ★★ 覆盖策略（v1.2 重写）：两阶段原地替换

#### 先说清楚为什么**不**照搬 Velopack 的「stub + 版本目录整体切换」

Velopack（现代 .NET 桌面自更新框架）的做法是：根目录只放一个几十 KB 的 stub `YourApp.exe`，真正的程序在 `current\` 里，更新时**把整个 `current` 目录换掉**，逼近原子切换。它很优雅，本机实测也**确实可行**（§4.10 实验 E），但**对本工具不适用**：

| # | 理由 | 说明 |
|---|---|---|
| ① | **我们是绿色版** | 用户解压到任意位置、直接双击 `TFAC剧情箱-轮椅版.exe` 就用。Velopack 的布局**必须由安装器创建**，一转过去所有已保存的快捷方式、用户习惯的路径、`Pakout.ps1` 的出包形态都要跟着改，还得额外写一个"从平铺布局迁移到 stub 布局"的一次性迁移器。成本远大于收益 |
| ② | **我们不需要它最大的那个卖点** | Velopack 用整目录替换，核心收益是「用户数据不在 `current` 里，所以更新冲不掉」。而本工程的数据**本来就不在安装目录**：`settings.json` 在 `%AppData%\GalExcleTools\`（`Services\AppSettingsService.cs:13,16`）、`runtime.log` 在 `%LocalAppData%\GalExcleTools\Logs\`（`MainWindow.xaml.cs:55-59`）→ **这份收益对我们恰好是零** |
| ③ | **实测让"原地替换"反而更安全了** | §4.10 实验 A / C 证明：运行中的 exe **能改名、腾位后能写新文件**，`MoveFileEx` 直接替换都返回成功。所以原地替换**不再要求"必须先彻底退出进程才能工作"**（我们仍然会要求退出，那是作为一致性保险，不是技术前提） |
| ④ | **原地替换保住路径稳定性** | 更新前后 exe 路径、脚本相对路径、快捷方式全不变 —— 出问题时的排查成本低得多 |

**但要吸收 Velopack 的三条经验**：

- **updater 的 CWD 与脚本位置都必须在安装目录之外**（§9.3）；
- **覆盖前预检"谁锁着安装目录"**（CWD / 独占句柄 / 杀软），拿不准就拦住（§9.7）；
- **回滚能力**：Velopack 靠保留旧 `current` 目录，我们靠「延迟一轮清理的 `*.old-{ver}`」（§9.5）—— 效果等价，且**不需要额外那一份整目录拷贝**。

#### 替换算法：两阶段 + 可回滚

先算动作集合，再**整批**走两个阶段 —— "整批"是关键：

```
准备：算出动作集合
  ToReplace = 包内存在 且 与安装目录现有的不同（大小或 SHA-256 不同才动手，相同就跳过）
  ToDelete  = 安装目录存在、包内不存在、且落在白名单内
  Skip      = 白名单外的一切（用户自己塞的东西，永不触碰）

阶段 1 —— 整批腾位（对所有 ToReplace ∪ ToDelete 的旧文件）
  MoveFileExW(src, src + ".old-{TargetVersion}", MOVEFILE_REPLACE_EXISTING)
  ★ 不指定 MOVEFILE_COPY_ALLOWED（微软官方明确要求），保证是"同卷改名"而不是跨卷复制
  ★ 任一文件腾位失败 → 立刻停止，把已经腾位的按【逆序】改回原名 → 报错 exit 5

阶段 2 —— 整批落位
  把 staging 里的新文件逐个复制到各自的目标原路径
  ★ 任一文件落位失败 → 停止，删掉本轮已落位的新文件，把阶段 1 腾位的全部改回原名 → 报错 exit 5

收尾
  ★ 本次产生的 *.old-{ver} **一个都不删**：它们就是回滚窗口（§9.5），只把路径记进待清理清单，
  由客户端在**下一轮启动**早期清理（那时"新版跑得起来"已经被真实验证过一次）
  —— 当场删掉等于没有回滚窗口，「新版装上去但起不来」时用户就只剩重新下载这一条路
```

**为什么是"两阶段整批"，而不是逐文件"删一个写一个"**：

- 「先删后写」在**正在运行的程序自己身上直接失败**（实验 A：运行中的映像删不掉）。逐文件删写会让 updater 在遇到的第一个 `.exe`/`.dll` 上就崩，而**此时已经删掉了一半文件** → 留下半个残废的安装目录，这是最坏的失败形态。
- 两阶段把「旧文件全部离开原位」和「新文件全部落位」分成两个整批，**每一批都能整体逆序回滚**，尽可能逼近目录整体切换的原子性。
- 万一在阶段 2 中途断电 / 被杀，安装目录的形态仍然是明确可判定的（旧文件都在 `*.old-{ver}`，新文件落了一部分）→ 下次启动的**修复路径**是确定的：客户端检测到残留 `*.old-*` 且主 exe 缺失或版本与清单不符时，提示用户把 `*.old-{ver}` 改回原名（§9.5 / §14）。

#### 白名单

```
镜像（可删可换）范围：
    *.exe  *.dll  *.pri  *.xbf  *.winmd  *.json  *.config  *.pdb  *.xml  *.ico  *.png
    Assets\**   Tools\**            ← 程序资产，一并镜像
显式排除（本仓库实测会被运行时生成的目录）：
    Tools\**\__pycache__\**         ← Python 执行 Tools\**\*.py 时自动生成 .pyc
    Tools\**\*.pyc
保留（永不删除）：
    任何不在白名单里的文件 —— 用户自己放进来的东西
    UpdateStaging / *.zip.download / *.old-{ver}（工作文件，不属于安装目录的"程序文件"集合）
```

- **为什么 `__pycache__` 是"排除"而不是"删除"**：源 `.py` 改动后，`.pyc` 会因内嵌的 mtime/size 与源文件不匹配而**自动失效重编**，所以删不删都安全；但**打包侧必须排除**（否则把本机编出的 `.pyc` 发给用户，既增大体积，又可能因路径/版本差异出怪问题）。
- 目标路径匹配**必须大小写不敏感**（README.md:271 的硬规矩，这条踩过六次）。
- 白名单里**没有任何"删目录再重建"的操作** —— 只动文件，绝不整目录删。
- 替换 / 删除**不依赖任何备份**（§9.5）：旧文件被原地改名成 `*.old-{ver}` 留着，那就是回滚用的那一份，等下一轮启动确认新版能跑再清理。

### 9.7 多实例预检

本工程**没有单实例守卫**，用户完全可能开两个。此时覆盖必然因文件占用失败，而且是在「主程序已经退出」之后才失败 —— 最坏的失败时机。

**做法**：在「用户点确认下载」**之前**先预检：
```
按 exe 基名找进程（Process.GetProcessesByName(exeBaseName)），
逐个比对 MainModule.FileName 是否等于当前 exe 路径；
命中数 > 1 → 直接中止并提示「检测到另一个本体工具正在运行，请先关闭它再更新。」
（读 MainModule 可能因权限抛异常 → catch 住，按「疑似有另一个实例」处理 —— 宁可拦住）
```

### 9.8 ★ 杀软拦截：自更新最大、也最容易被忽略的风险

社区一致结论（多个来源）：**Windows Defender 及第三方安全软件对新生成的、它不认识的 EXE 会无条件拦截**，表现为「阻止您的软件启动（可能无任何提示）」——即**更新完成后新版本双击起不来，而用户完全不知道为什么**。而且：

> 「**一个新的下载地址、新的文件被下载出于安全的顾虑会无条件的阻止或警报**（即使软件加了数字签名、没有过界行为等等）。一般放几天以后就不会再提示了。」

**对策（本项目能做的）**：

1. **回滚窗口是硬要求**（§9.5）→ `*.old-{ver}` 旧文件就是救命稻草。**必须在错误信息里给出「把 `*.old-…` 改回原名」的手工恢复步骤**，而且这个提示要在 **updater 窗口里**、关机前就能看到。
2. **保留一份「可手工双击启动的旧 exe」**：`*.old-{ver}` 里天然有一份完整可运行的旧版本 → 明确告诉用户「如果新版本起不来，把程序目录下的 `TFAC剧情箱-轮椅版.exe.old-1.0.0` 改名回 `TFAC剧情箱-轮椅版.exe`（去掉 `.old-…` 后缀）就能用回旧版本」。
3. **更新成功后不要立刻删 `*.old-{ver}`** —— 延迟到下一轮启动再清（§9.5）。
4. 发布侧：**发 zip 不发裸 exe**（我们就是 zip）；向 Microsoft WDSI 提交误报申诉时，**提交的样本必须与对外发布的包逐字节一致**。这些属于发布侧（附录 B）。
5. 不要设置开机自启（社区明确点名这是被判"不受欢迎行为"的项）。


### 9.9 READY 握手（保留，硬要求）

- 客户端生成信号路径：`%LOCALAPPDATA%\GalExcleTools\UpdateRunners\UpdaterReady-{yyyyMMdd-HHmmss}-{Guid:N}.signal`
- 启动 updater 后轮询该文件（`Task.Delay(250)`），**总超时 90 秒**；
- 文件内容含 `READY`（OrdinalIgnoreCase）→ 进度「热更新程序已完成预检。」/「主程序即将退出并开始覆盖。」→ 然后才 `Application.Current.Exit()`；
- 90 秒内没等到 → `TimeoutException`「热更新程序预检超时。」，**主程序继续运行**（不退出），把 updater 窗口留给用户看错误原因。

**退出前必须做的收尾**（源项目没有这一步，本工程有防抖保存 → 不做会丢数据）：
```csharp
FlushPendingCharacterInfoSave(); FlushPendingSkillsSave();
FlushPendingBuffsSave();         FlushPendingDraftSave();   // 见 MainWindow_Closed 既有做法
ToolboxLog.Info("主程序即将退出以完成热更新。");              // 并确保日志 sink flush
```
> **实施前置检查项**：先确认日志 sink 有没有 flush/dispose 出口（README 说日志按 8MB / 跨天轮转，如果写盘是异步的，不 flush 会丢掉最后几行）。
>
> ✅ **2026-10-05 查证结论：不需要额外 flush。** `Services\Logging\RuntimeLogFile.cs:97` 的 `AppendLine` 是
> `File.AppendAllText(path, line + Environment.NewLine, Utf8NoBom)` —— 每写一行就开/关一次文件，进程被杀也不会丢已写入的行；
> `IToolboxLogSink` 的实现在 `MainWindow.Logging.cs:455`（`ToolboxLogBridge`），只把消息 `RunOnUiThread` 追加到面板，不持有文件句柄。
> 所以退出路径上只要照上面调四个 `FlushPending*` 就够了（多实例/日志轮转都不受影响）。

### 9.10 ★★ 运行前置 + 覆盖器加固（2026-10-06 追加）

> 出处：Microsoft Learn [Distribute an unpackaged WinUI 3 app](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app)（2026-10-02 更新）
> 原文：**No package identity** — Without a package manifest, your app cannot use manifest-based Windows features:
> **no automatic updates via App Installer or Store**, ...；**Runtime dependency** — The Windows App SDK runtime
> must be present on the user's machine. You must either **bundle the runtime installer** with your app, or use
> self-contained deployment.
> 我们的验证：把框架依赖的 2.0.4 产物在本机（只装了 `Microsoft.WindowsAppRuntime.2` 的 2.2/2.3/2.4/2.5）启动 ——
> **起来了**。所以判定条件必须是「家族 + 版本 ≥ 要求」，**不能要求恰好 2.0.x**；同时 `1.x` 的家族名带次版本
> （`Microsoft.WindowsAppRuntime.1.8`），`2.x` 只带主版本（`Microsoft.WindowsAppRuntime.2`）—— 两种形态都要试。

#### 9.10.1 为什么要做（一次真实的缺口）

第 5 步把 Windows App SDK 改成**框架依赖**后，包里不再带运行时 dll（省掉约 19 MB）。
官方文档对这一形态的要求是：**随包提供运行时安装器**，否则目标机器没装运行时 = 新客户端**双击打不开**。
本工程当时既没带安装器、也没有任何检查 —— 这是个"装完才发现打不开"的缺口。

#### 9.10.2 判定与动作

| 环节 | 规则 |
|---|---|
| 出包 | `update-package.json` 写 `windowsAppSdkRuntime`：程序目录里**有** `Microsoft.WinUI.dll`（投影）但**没有** `Microsoft.ui.xaml.dll`（原生）⇒ 框架依赖，值 = csproj 里 `Microsoft.WindowsAppSDK` 的 major.minor（`2.0`）；否则空串 |
| 覆盖器预检 | 值非空时查运行时：家族 `Microsoft.WindowsAppRuntime.{major.minor}` **或** `Microsoft.WindowsAppRuntime.{major}`，版本 ≥ `{major.minor}.0` |
| 缺运行时 | **中止更新，一个文件都不覆盖**（放在 READY 之前 —— 主程序还没退，用户看到的只是"这次更新没做"），并给安装器地址 |
| 带了安装器 | 传 `-RuntimeInstallerPath` ⇒ 走静默安装 `WindowsAppRuntimeInstall.exe --quiet --force`，装完**复查**一次；复查不过照样中止 |
| 自动化 | `-SkipRuntimeCheck`（只在明确知道自己在做什么时用） |

安装器的静默参数来自**安装器源码**（`microsoft/WindowsAppSDK` 的 `installer/dev/main.cpp`）：
`-q`/`--quiet`、`-f`/`--force`、`-r`/`--repair`、`--msix`；且 `if (!isElevated && !quiet)` —— **quiet 模式不需要提权**。

> ⚠️ **生效时机（重要）**：覆盖器脚本是客户端从**安装目录**抄到 `UpdateRunners` 再跑的（§9.3），
> 所以**一次更新执行的是"当前已装版本"的脚本**。运行前置只对"**从带它的版本往后**"的更新生效 ——
> 老客户端（2.0.4 及以前）升到框架依赖版时**不会**检查运行时。

#### 9.10.3 覆盖器加固（两条"绝不能发生"）

| 风险 | 原来的行为 | 现在 |
|---|---|---|
| **腾位窗口里没有可启动的 exe** | 入口 exe 也参与"整批改名"，改名后到落位前，安装目录里**没有 exe**；此间被硬杀/断电 ⇒ 用户双击没反应 | 入口 exe **不参与改名**：腾位阶段改成"**拷贝**一份 `*.old-{ver}`"，落位阶段在原位直接覆盖（**任何时刻都有一个可启动的 exe**）；顺序上它**腾位排最后、落位排最前** |
| **回滚失败** | 一次性 `File.Move`，目标已存在或被占用就抛；catch 里只打印一行，且**回滚本身会中断** | 回滚统一走 `Invoke-ZdRollback`：① 先清位再改名；② 每项**重试 5 次 × 300ms**；③ **跑完不中断**，失败项汇总；④ 失败清单写 `UpdateLogs\回滚失败-*.log` 并在控制台红字列出 |

配套的"最后一根救命稻草"：**腾位之前**就往安装目录写 `修复更新.cmd` + `修复更新.ps1`（把 `*.old-{版本}`
改回原名，带重试、不碰白名单外的文件）。更新**成功**或**回滚干净**时立刻删掉；只有"脚本被硬杀 / 回滚没跑完"
才会留下 —— 那正是用户需要它的时候。客户端**下一轮启动**的清理（§9.5）也会顺手收掉它。

**实跑验证**（2026-10-06，临时目录，未碰真实安装目录）：

| 用例 | 结果 |
|---|---|
| 运行时检测 `2.0` / `1.8` / `1.5` / `9.9` | `True` / `True` / `True` / `False` —— 修正了"1.x 家族名带次版本"这个 bug（第一版把 1.8 判成 False） |
| 一键修复脚本（造半更新状态：exe/lib 已覆盖、一个孤立副本） | 3 个文件全部恢复、无关文件未动、无 `.old-` 残留、自身可被收掉 |
| 覆盖正常路径 | 替换 3 / 删除 1 / 回滚窗口 3 / 待清理清单写入，白名单外不动 |
| 注入失败（落位时目标文件不存在） | 抛"已完整回滚到更新前"，目录**逐字节**回到更新前，无任何残留 |

> 顺带修掉一个 PS 语法坑：**`New-Object X()` 这种无参写法是解析错误**（`"(" 后应为表达式`），
> 只有带参数的 `New-Object X($arg)` 才会被当成方法调用。改用 `[System.Text.Encoding]::ASCII`。



### 9.11 ★★ 增量更新（delta，2026-10-06 追加）

#### 9.11.1 一句话

整包里 **96% 的字节是没变的**（.NET 运行时、Windows SDK 投影、打包的 Python）。增量更新就是
"只把变了的几个文件打一个小包，让客户端下它"。**判定靠内容哈希，不看时间、不看文件名。**

#### 9.11.2 发布侧怎么知道哪些是新文件

1. 每版出包时给**进包文件**逐个算 SHA-256，写成 `file-index.json`（相对路径 → 大小 + 哈希；448 个文件约 77 KB）。
2. 下一版出包时拿上一版的索引（优先读它的 `file-index.json`；没有就**现算**它那份程序目录，实测 2.8 秒）与新目录**逐文件比**：

   | 情况 | 判定 |
   |---|---|
   | 新目录有、旧索引没有 | 新增 |
   | 两边都有但大小或哈希不同 | 变化 |
   | 旧索引有、新目录没有 | 删除 |

3. 变化 + 新增的文件打进 `…-delta-from-v{基准}.zip`，删除项写进包内清单的 `delete[]`；
   每个变化文件再带一份**旧内容哈希** `baseSha256`（覆盖器落地前核对，见 §9.10）。

两条容易忽略的性质：
- **内容是内容**：重编译一次但产物字节相同 → 判定"无变化"，不发增量包（同版本对同版本实测返回"逐文件相同"）。
- **脚本也是文件**：`Scripts\热更新覆盖.ps1` 会跟着版本一起进增量，所以覆盖器**自己**也能被热更 ——
  v2.1.1 的增量里就有它，2.1.0 的用户升上来之后，盘上的覆盖器才第一次带上 delta 闸门与运行时前置。

#### 9.11.3 实测数字（这是做它的理由）

| 一跳 | 整包 | 增量包 | 变化 / 删除 | 省 |
|---|---|---|---|---|
| 2.0.3 → 2.0.4（框架依赖瘦身那一跳） | 76.41 MB | 3.11 MB | 4 / 274 | 96% |
| 2.1.0 → 2.1.1（常规发版） | 76.42 MB | 3.09 MB | 4 / 3 | 96% |

增量包那 3 MB 拆开（2.0.3→2.0.4 实测）：应用 dll 2,965,687 B、exe 244,975 B、pri 38,305 B、
deps.json 4,248 B、包内清单 2,345 B。

#### 9.11.4 客户端与覆盖器

- 客户端：清单里 `delta` 段 + 本机版本 == `baseVersion` + 增量更小 → 下增量；否则整包（§8.3 契约）。
- 覆盖器：`-CurrentVersion` 对齐 + `files[].baseSha256` 逐个核对；**镜像语义在增量模式下关掉**
  （否则"没变"会被当成"该删"），删除项只认 `delete[]` 且先过白名单。
- 落地复用整包那一套：两阶段替换 / 回滚窗口 / 一键修复 / 运行时前置 —— 增量没有自己的落地逻辑。

#### 9.11.5 回归怎么锁

| 用例 | 位置 | 锁住什么 |
|---|---|---|
| `update-delta-selection` | C# 回归套件 | 选择规则五条分支（基准对/版本不对/增量更大/老清单/哈希写坏） |
| `updater-overlay-delta` | C# 回归套件（真跑脚本） | 只替换包里带来的、**没变的一个字节都不动**、删除清单生效、`.old-` 回滚窗口照旧 |
| `updater-overlay-delta-added` | C# 回归套件（真跑脚本） | 包里**带新增文件**（按契约没有 `baseSha256`）时照样装得上 —— 2026-10-08 那次事故的形状 |
| `updater-overlay-delta-reject` | C# 回归套件（真跑脚本） | 版本不符 / 指纹不符 / 脏指纹 → 退出码非 0 且**一个文件都不动** |
| `Tests\Test-ZdDelta.ps1` | 独立脚本（pwsh 7） | 出包侧纯逻辑：索引、找基准版、生成增量包、包内清单字段、两条"不发增量"的边界 |

> 覆盖器那两条是**真的起 powershell.exe 跑脚本**（沿用 `updater-overlay-*` 的既有做法），
> 不是模拟 —— 闸门写错会当场红。

#### 9.11.6 踩到的坑（都修了）

| # | 坑 | 教训 |
|---|---|---|
| 1 | 抽取"增量步骤"函数时，一次字符串替换**把清单写入那一行也吞掉了** → 全量出包路径根本没写过 `toolbox-update.json`；随后函数又去读这份还不存在的清单，StrictMode 直接抛"找不到属性 `assets`" | 大段替换后**必须回读确认**；DryRun 只走复用路径救不了全量路径 —— **两条路径都得试** |
| 2 | 复用路径重生成清单时把 `delta` 段抹掉（`Write-ZdRefreshedManifest` 不认识它） | 抽出 `Update-ZdDeltaArtifacts`，**两条路径共用**；凡是"只在一条路径里加的东西"，另一条路径迟早吃掉它 |
| 3 | 覆盖器的包根解析要求"包里必须有 entryExe 那个文件"，可**增量包通常不含 exe** | 只有整包才做"文件必须在包里"的检查；增量包只要求字段写着（用来映射包根↔安装目录） |
| 4 | `Set-StrictMode` 下访问不存在的属性会抛（老清单没有 `delta`、新增文件没有 `baseSha256`） | 读可选字段一律 `$obj.PSObject.Properties['x']` 或先判空；C# 侧对应的是可空属性 |
| 5 | 第 4 条的**后半截当天又踩了一次**（2026-10-08）：整包那条修好之后，`Assert-ZdDeltaPrecondition` 里 `$entry.baseSha256` **还是直接点属性** —— v2.2.0 的增量包里有 9 个新增的 `Tools\Audio\ffmpeg\*`（按契约它们没有 `baseSha256`），于是 2.1.2 → 2.2.0 的增量更新全挂在"解压"那一步、退出码 6、一个文件都没动 | **同一条规矩要一次扫干净**：修完一处，把文件里同类写法（`$x.可选字段`）全找一遍；回归也得补上**带新增文件的增量包**这个形状（原来三条增量用例的每个文件都能算出旧指纹，所以一次都没触发）—— 见 `updater-overlay-delta-added` |

### 11.6 检查状态机（fail-closed）：只有「已确认」才允许进入覆盖

借鉴 PC 端 `P\src\launcherNetworkPolicy.ts:1-13` 的四态闸门（`checking / ready / updateRequired / verificationFailed`，**只有 `ready` 放行网络动作**）。我们的场景里没有"下载业务要放行"，但**同样需要一个闸门**：**版本状态没确认清楚时，绝不允许点「立即更新」**。

```csharp
public enum UpdatePhase { Idle, Checking, Ready, UpdateAvailable, Failed }
```

| 状态 | 含义 | 允许的动作 |
|---|---|---|
| `Idle` | 没查过 / 用户关了自动检查 | 只能「检查更新」「测试连接」 |
| `Checking` | 请求进行中 | 只能「取消」 |
| `Ready` | 已确认「当前就是最新版」 | 只能「检查更新」 |
| `UpdateAvailable` | 已确认有更高版本，**且** §6.4 的 `plan` 齐全（版本 / 文件名 / 大小 / SHA-256 / runtime 五项） | **只有这个状态**允许进入下载与覆盖 |
| `Failed` | 任何一步失败（网络 / 403 / 404 / JSON 坏 / 哈希不符） | 只能「检查更新」重来；**绝不退化成"已是最新"** |

三条硬规则：

1. **`Failed` ≠ 「已是最新版本」** —— 借鉴 Android 2026-09-30 事故（清单站点连不上就把用户锁死，连错误日志都传不出去）。失败时保留上一次的版本信息展示，只把「上次结果」写成失败原因。
2. **`Ready` / `UpdateAvailable` 只能由一次完整检查产生**，不允许由缓存或猜测进入 —— 落盘的只有检查**时间**，结论文本不落盘、更**不是**状态机输入。
3. `UpdateAvailable` 的判定是**两维**：语义版本更高 **且** 包元数据齐全（`plan` 五项齐）。任一维缺失都退回 `Failed` —— 这是 Android `versionCode` 事故的直接教训（§20.4）。

## 12. 设置项落盘：枚举怎么塞进只有 bool 的撤销栈

现状（已核实）：`SettingsViewModel.SetSettingProperty` **只有 `bool` 重载**，撤销条目 `SettingUndoEntry(... bool OldValue, bool NewValue)` 也只存 bool。

**方案 A（推荐，改动最小、撤销语义天然正确）** —— `AppSettings` 里照旧存 `UpdateChannel` 字符串，ViewModel 对外暴露 **bool**：

```csharp
public bool UseBetaChannel          // true = 测试版
{
    get => string.Equals(_settings.UpdateChannel, "beta", StringComparison.OrdinalIgnoreCase);
    set => SetSettingProperty(ref _useBetaChannel, value, nameof(UseBetaChannel),
             "更新通道", () => _settings.UpdateChannel = value ? "beta" : "stable",
             () => { OnPropertyChanged(nameof(UpdateChannelText)); OnPropertyChanged(nameof(UpdateChannelIndex)); });
}
public int UpdateChannelIndex { get => UseBetaChannel ? 1 : 0; }   // 给 ComboBox 用（只读单向）
public string UpdateChannelText => UseBetaChannel ? "测试版 / Beta" : "正式版 / Release";
```
ComboBox 的 `SelectedIndex` 绑 `UpdateChannelIndex`（只读），`SelectionChanged` 事件里写 `Settings.UseBetaChannel = index == 1;`
→ 完全复用既有 bool 重载 + 既有撤销栈 + 既有 `Save()`，**不动 `SettingUndoEntry`**。

**方案 B**：给 `SetSettingProperty` 加 `int`/枚举重载，并把 `SettingUndoEntry` 改成泛型 → 动的是**所有设置项共用的撤销机制**，风险面大得多。**不建议**，除非以后还要加别的枚举设置。

**脏值处理**：`LoadBindableSettings()` 里读取时必须兜住手改 `settings.json` 的情况（照抄同文件里处理非法 `UpdateSource` 的既有套路）：
```csharp
_useBetaChannel = string.Equals(_settings.UpdateChannel, "beta", StringComparison.OrdinalIgnoreCase);
// 通道字符串不认识 → 回落 stable，并把 settings 里的值纠回去
```

## 13. 日志

- **同一个状态不重复写日志**（借鉴 Android 的 `status|message` 签名去重，`UpdateStateStore.java:34-55`）：下载进度只记「开始 / 每 10% / 结束」三档，否则一个 100MB 包就能把 `runtime.log` 写爆。
- 客户端侧全部走 `ToolboxLog`（`Info`/`Warn`/`Error`），**每个 catch 都要有出口**（README.md:269；棘轮 ① 盯的就是裸 `catch`）。
- 关键节点各记一行：检查开始/结果（含选中 tag 与版本）、配额剩余量、下载开始（含大小）/完成、校验通过/失败（含实际 SHA 前 8 位）、启动 updater（含 pid 与脚本路径）、收到 READY、预检超时、退出前收尾、失败时的 HTTP 状态码与 body 片段（403 限流文案要原样记下来，这是排查的唯一线索）。
- **每个 `catch` 的日志要写"为什么吞"**，例如 `ToolboxLog.Warn("读更新缓存目录失败，按没有缓存继续。", ex);`
- updater 侧日志：
  - ⚠️ **不要用 `Start-Transcript` 写固定文件名**：实测/官方 issue（`PowerShell#13677`）——**目标文件已存在时 `Start-Transcript` 会用有损 ASCII 编码**，中文变问号。我们的做法是**每次新文件名** `Update-{yyyyMMdd-HHmmss}.log`，天然规避；若将来要追加写，必须显式 `Out-File -Encoding utf8`。
  - 脚本文件本身必须 **UTF-8 with BOM**（Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI 解析，中文会乱码/报错）——源项目的 `Convert-FileToUtf8Bom` 这一步要保留。
- 更新成功后第一次启动，记一条 `ToolboxLog.Info`（原计划写进 `UpdateLastStatus`；该字段 2026-10-06 已删除）（用 `--updated-from <版本>` 参数从 updater 传给新进程，App 在 `OnLaunched` 里解析并清账）。

## 14. 安全与回滚

| 风险 | 防线 |
|---|---|
| 半截包被当成完整包 | `.download` 临时名 + `File.Move` 原子改名 |
| 下到 HTML 错误页 | 校验 HTTP 状态码 + **zip magic `50 4B 03 04`**（§8.1 ⑥） |
| 包被替换/发错 | 大小 + SHA-256 双层；SHA 来自同渠道的 Release 附件清单 |
| 包里是别的产品的包 | `update-package.json` 四层校验（客户端一次、updater 解压后再一次） |
| zip-slip 目录穿越 | 解压前自己扫条目名（§9.4）+ 复制前 `Assert-Inside` |
| 预检失败但主程序已退出 | **READY 握手**：不写 READY 主程序不退出 |
| 覆盖到一半失败 | updater 保留窗口 + 打印错误 + 退出码 + 提示手动下载 + **`*.old-{ver}` 改名恢复步骤** |
| **杀软拦截新 exe（起不来）** | `*.old-{ver}` 里留着一份完整可运行的旧版本，且清理被延迟到"下一轮启动"（§9.8 / §9.5） |
| 主程序不退（用户不关/卡死） | updater 等 30 秒后中止，**不做强杀**（强杀可能损坏工程数据） |
| 多实例占用 | 更新前预检（§9.7），直接拦住 |
| 状态混乱（半个新版本） | **白名单镜像**（§9.6）不给"新旧混用"留机会；**两阶段整批替换 + 逆序回滚**保证中途失败能退回起点 |
| **updater 自己把安装目录锁死**（v1.1 的真实 bug） | 脚本与 CWD 都放在 `%LOCALAPPDATA%\GalExcleTools\UpdateRunners\`（§9.3 / §4.10 实验 H） |
| 更新中途断电 / updater 被杀 | 安装目录形态可判定（旧文件在 `*.old-{ver}`）→ 下次启动检测到残留即提示把 `*.old-{ver}` 改回原名（§9.6 收尾 / §9.5） |
| 时效 URL 被缓存 | 只存 `browser_download_url`，落地 URL 每次重新解析 |
| 磁盘不够 | 预检可用空间 ≥ 包大小 × 3（包 + 解压后的 staging + 一轮 `*.old` 旧文件），不够就提示清理 |
| 限流把 IP 打死 | 请求预算（§7.3） |

**回滚**：不做整目录备份（O3，§9.5）。唯一回滚手段是两阶段替换**留在原地**的 `*.old-{版本号}` —— 把后缀去掉就是更新前的完整程序，旧 exe 可以直接双击运行。清理被刻意延迟到"下一轮启动确认新版跑得起来"之后，所以"新版装上去但起不来"这个最危险的形态一定落在回滚窗口内。**窗口外的退路**只有重新下载上一版 Release 包（发布侧必须保留最近 2~3 个版本，§9.5）。

| `updater-overlay-locked-file` | 用一个子进程**独占打开**（`FileShare.None`）安装目录里的某个 `.dll` 后再跑 updater → 断言退出码 5 且**目录内容一字未变**（对应 §4.10 实验 D） |
| `updater-cwd-not-installdir` | 断言启动 updater 时 `ProcessStartInfo.WorkingDirectory` **不等于** `AppContext.BaseDirectory`，且脚本实际路径在 `%LOCALAPPDATA%\…\UpdateRunners\` 下（对应 §4.10 实验 H，v1.1 的真实 bug） |
| `applyplan-whitelist` | 纯逻辑单测：给一批路径（含 `Tools\Atlas\python\Lib\site-packages\PIL\__pycache__\x.pyc`、`用户笔记.txt`、`TFAC剧情箱-轮椅版.exe`、大小写变体 `tools\ATLAS\X.PY`）→ 断言分类集合与 §9.6 白名单逐条一致（大小写不敏感） |
| `updater-overlay-bad-sha` | `-ExpectedSha256` 给错 → 退出码 3、**没有**写 READY、**没有**动安装目录 |
| `updater-overlay-bad-manifest` | 包里 `toolboxStableKey` 改成别的 → 被拒、没有写 READY |
| `updater-zip-slip` | 包里用 `..\` 构造越界路径 → 被条目扫描拦下，退出码 4 |

> `updater-*` 是**真执行 PowerShell** 的行为断言（秒级，不扫源码），它们把 updater 的契约锁住，比「源码里有这个字符串」强得多，而且**不增加棘轮 ⑤ 的读源码调用点**。

### 18.3 ★ O10 的评估结论：为什么**不**引入 GeneralUpdate

你给了「你觉得哪些更优就用什么」的判断权，我的结论是 **维持自研**。它的现状我核实过（读 Gitee 仓库页）：

| 事实 | 说明 |
|---|---|
| `https://gitee.com/GeneralLibrary/GeneralUpdate`，**Apache-2.0**，655 star / 195 fork / 1347 次提交，最新标签 `v10.5.0-beta.7` | 是个**在维护的真项目**，不是玩具；许可宽松，商用无碍 |
| 仓库结构 `src/`（C#）+ `tests/` + `docs/` + `imgs/` | 有文档、有测试，工程化程度可以 |
| 它的模型 = **"客户端 exe + 独立升级器 exe" + 自己的 `version.json` 契约 + 自己的目录布局** | 这是决定性的一条 |

**不引入的四条理由**（按重要性排序）：

1. **它解决的不是我们最难的那部分。** 我们这轮的成本几乎全花在 Gitee 本身：`prerelease` 在官方 swagger 里声明 string、实测才是 bool（§4.7）；匿名配额 60 且按 IP 计；403 有两种含义；两级 302 带时效 token；**没有 Range**；单附件 100MiB / 仓库 1GB（§4.8）。这些**接谁都得自己写**。它替我们省掉的只是"替换文件"那一段 —— 而那段恰恰已被 §4.10 的 16 组本机实测定死成**两阶段原地替换**，代码量本来就不大。
2. **契约要改成它的。** 双通道（beta / 正式）是直接映射 Gitee Release 的 `prerelease` + §6 的三个 JSON；换成它的 `version.json` 就得把那套语义塞进它的字段里，**反而多一层映射**，而且它的字段模型不保证能表达"beta 通道故意挑预发布版"。
3. **进程与目录布局必须跟着它走。** 它是多 exe + 版本目录的模型，与"win-x64 自包含绿色版、用户可能放在 `D:\本工具\`、目录带中文"的现实不匹配；我们自己的 updater 是**一个只读包内清单、逻辑与版本无关的 ps1**（§9.3），刻意做到不需要被更新。
4. **自更新工具再依赖一个自更新框架 = 多一层"自己也要升级"的东西。** 它自己发版、自己改契约，都要我们跟。

**真正值得借的只有一样**：它的**增量更新（bsdiff）**。但那要求发布侧为**每一对版本**出补丁（N 个版本 → N-1 个补丁），属于附录 B 的出包侧工作，本轮不做。

> **复核条件（什么时候回头找它）**：等 §4.8 的两道墙真的顶上来 —— 实测**打包后 zip 超过 100MiB**、或"保留最近 2~3 版"撑破 1GB 总量 —— 再评估。那时正确的做法是**只借增量算法**（或改为分包资产），**仍然不引整个框架**。

## 19. 关于 RID（你让我先解释清楚的那件事）

> ✅ **已拍板：方案 C**（你的答复「1，c」）。下面保留三个方案的完整对比 —— 它同时是决策记录，以及"将来要加 x86 / arm64 时该怎么做"的依据。

### 19.1 `RuntimeIdentifier` 是什么

.NET 的 RID 决定**这一包二进制是给哪种 CPU 架构/操作系统的**。WinUI 3 应用的 .NET 运行时必须**自包含发布**（`SelfContained=true`，本项目不变）；
而 Windows App SDK 那一层自 2026-10-06 起改为**框架依赖**（`WindowsAppSDKSelfContained=false`，见 §3 注）——
所以包里仍有一整套跟架构绑定的 .NET 文件（`TFAC剧情箱-轮椅版.exe` + `*.dll` + `.pri`/`.xbf` 资源），但不再带 WinUI 的原生运行时。

本工程 `GalExcleTools.csproj`：

```xml
<Platforms>x86;x64;ARM64</Platforms>
<RuntimeIdentifiers>win-x86;win-x64;win-arm64</RuntimeIdentifiers>
```

`RuntimeIdentifiers`（**复数**）是"我支持这几个"，不是"我就是这个"。实际打哪个由 `dotnet publish -r <RID>` 决定 —— `Pakout.ps1` 的 `-Runtime` 默认就是 `win-x64`。

### 19.2 三个选项与代价

| 方案 | Release 附件 | 客户端行为 | 代价 |
|---|---|---|---|
| **A. 只发 win-x64** | 1 zip + 1 sha256 + 1 清单 | 服务端硬校验 `runtime == "win-x64"`；找不到明确报「没有 win-x64 更新包」 | **x86 / ARM64 用户拿不到热更新**（但本项目至今只在 x64 上验证过） |
| **B. 三个 RID 都发** | 3 zip + 3 sha256 + 1 清单（`assets` 三项） | 按进程架构挑（`RuntimeInformation.ProcessArchitecture` → `X64→win-x64` / `X86→win-x86` / `Arm64→win-arm64`） | 构建时间 ×3、**每个 Release 占 ~300MB 仓库附件配额 → 三个 Release 就把 1GB 用光**；单附件还有 100MiB 上限 |
| **C. 先只发 win-x64，模型留多 RID**（= A 的结构 + B 的余地） | 1 zip | 同 A | 无额外代价 —— **本设计就是 C** |

### 19.3 为什么强烈建议 A/C

1. **本项目目前只在 x64 上验证过**：README.md:220-224 明确要求构建用 `-p:Platform=x64`；回归测试与 `--ui-smoke` 都是 x64。
2. **Gitee 容量是硬墙**（§4.8）：单附件 ≤100MiB、**每仓库附件总量 ≤1GB**。源项目那个包 101,305,834 字节 ≈ 96.6 MiB 已经贴着单附件上限；本工程包更大（内置 CPython + Pillow）。**三个 RID × ~100MB = ~300MB/Release → 三个 Release 就爆仓。**
3. **ARM64 用户极少**：WinUI 3 的 ARM64 自包含发布还有额外坑（原生依赖），而本工具是给 UE 角色美术流程用的，工作机基本 x64。
4. 将来真要发 x86/arm64，**结构不用改**，只是多挂附件 —— 这就是 C 的意义。

### 19.4 客户端实现差别

```
方案 A/C：
  SelectRuntimeAsset(manifest)
      → manifest.assets.FirstOrDefault(a => a.runtime.Equals("win-x64", OrdinalIgnoreCase))
      → null → 「发现 {ver}，但没有 win-x64 更新包。」
```

```csharp
// 只有方案 B 才需要
public static string GetCurrentRuntimeIdentifier() =>
    RuntimeInformation.ProcessArchitecture switch
    {
        Architecture.X64   => "win-x64",
        Architecture.X86   => "win-x86",
        Architecture.Arm64 => "win-arm64",
        var other          => throw new NotSupportedException($"不支持的进程架构：{other}")
    };
```

**`win-x86`/`win-arm64` 字符串必须大小写不敏感比较**（README.md:271 的硬规矩，这条踩过六次）。

### 20.4 两条最贵的教训（已转成硬规则）

**① 升级判据必须至少两维；任一维"回退"都会把用户彻底锁死。**
Android 端启动器 `1.1.3` 被误发布成 `versionCode = 1001003`，而游戏 APK 是 `versionCode = 1` → Android 拒绝"Code 降低"的覆盖安装 → 那批用户**再也装不回游戏**，只能重下约 **1.9 GB** 资源。
→ 落到本设计：版本判定**语义版本优先、不做数字 code 兜底**；`UpdateAvailable` 必须「版本更高 **且** 包元数据齐全」两维同时成立（§11.6 规则 3）；`update-state.json` 里 `targetVersion` 低于当前版本时**一律丢弃，永不降级**（§6.4、测试 `update-state-resume`）。

**② 「清单拉不到」绝不等于「必须升级 / 不能用了」。**
Android 2026-09-30 事故：清单站点连不上，客户端却把用户**锁死**在更新流程里，连错误日志都传不出去。
→ 落到本设计：任何检查失败都只是「检查失败」，主功能（Unreal 同步等）**完全不受影响**，且必须呈现为可恢复的提示（§7.2、§11.6 规则 1、测试 `update-check-failure-not-fatal`）。

> 顺带一个反向印证：**两个项目的发布脚本都把 Gitee 附件 100 MiB 上限硬编码了**（Android `Publish-AndroidLauncher.ps1:26`、PC `Publish-LauncherGiteePackage.ps1:19`/`:226-228`），`?per_page=100` 也都是写死的 —— 但**两边都没有处理限流 / 403 / 附件分页第二页**。§4.6 那份限流实测因此是这个项目里最有价值的一份证据。

## 21. 踩坑与经验记录（这些后期要同步做成知乎文档）

> 你的要求：「这些设计后期也会同步做成知乎文档，你需要什么坑或者经验就记得记录下来」。
> 所以这一节是**素材库**，不是设计的一部分。格式统一为：**现象 → 根因 → 对策 / 结论 → 证据**。
> 写文章时按 21.2~21.6 的主题成篇即可；**21.7 的方法论是最值钱的部分**，因为它可迁移到任何项目。

### 21.1 先给结论：这个项目里最反直觉的十件事

1. 运行中的 exe **可以改名**，但删不掉 —— 这就是"不重启就能换掉自己"的全部物理基础。
2. 包含未关闭句柄的**目录连改名都不行**，哪怕那个句柄已经允许 `FileShare.Delete`。
3. Gitee 的官方 swagger 把自己的字段类型写错了（`prerelease` 声明成 string，实际是 bool）。
4. Gitee 超限流返回的是 **403 + 纯文本**，不是 429 —— 而且那个 403 **不带任何 `X-RateLimit-*` 头**，客户端无法自证。
5. Gitee 的 `assets` 字段**不是 Release 附件**，是源码归档 zip。
6. Gitee 下载链**完全不支持 Range**，断点续传没法做（入口 URL 与落地 URL 都不支持）。
7. Gitee 的下载 URL 里那个 `token` **每次请求重新签发**，不能存。
8. WinUI 3 自包含应用的**整个目录是一致性整体**，只换 `.exe` 必崩。
9. 本机主程序名里有个**全角冒号**（U+FF1A），足以把 `cmd.exe` 中转启动整条路堵死。
10. 两个兄弟项目**都刻意不让客户端读 Gitee**，只有我们这个项目真的拿 Gitee raw 当清单源。

### 21.2 Gitee 平台（全部为本机实测，不是抄文档）

| # | 现象 | 根因 / 结论 | 证据 |
|---|---|---|---|
| 1 | 配额只有 **60**，**按 IP 计**（不是按客户端）；耗尽返回 **HTTP 403 + `text/plain` + 全文 35 字节 `403 Forbidden (Rate Limit Exceeded)`**，**不是 429** | 同一个 403 还有第二种含义（无权限）→ **必须结合 body 判断**，不能一律当限流 | §4.6 |
| 2 | 那个 403 响应**没有 `X-RateLimit-*` 头** | 客户端在限流发生时反而拿不到配额信息 → 只能靠**自己记账**（§7.3 请求预算） | §4.6 |
| 3 | 耗尽后 t+20s ~ t+240s 探测全 403，**隔 20 分钟以上仍 403** | 退避不能靠感觉；也不能"重试几次就好了" | §4.6 |
| 4 | 列表**默认只返回 20 条** | 必须写死 `?per_page=100`；两个兄弟项目的发布脚本也都写死了 | §4.3 |
| 5 | 官方 swagger 把 `prerelease` 声明为 **string**、`assets` 声明为 string，实测分别是 **bool** 和 **Object[]** | **官方 Response Class 整块不可信** → 必须用 `JsonElement` 防御性解析（`!prerelease` 这种写法会把字符串 `"false"` 当真值，正式版会被当预发布版） | §4.7 |
| 6 | `assets` 字段装的是 **源码归档**（`/archive/refs/tags/v1.6.0.zip`），不是 Release 附件 | 附件必须走 `/releases/{id}/attach_files`；落地路径里文件名会被**小写化**，`attname` 保留原大小写 | §4.2 / §4.5 |
| 7 | 下载链末跳带 `token` + `ts`，其中 `ts` 比请求时刻大 ≈2505600 秒（29 天，与 `Cache-Control: max-age=2592000` 一致） | **每次请求重新签发 → 绝不能持久化** | §4.5 |
| 8 | **Range 无效**：入口 URL 与落地 URL 发 `-r 0-1023` 都返回 **200 + 整包**，无 `Accept-Ranges`、无 `Content-Range` | 断点续传彻底不可行 → 设计里整条删除（Android 那边写了"服务端返回 200 就归零重下"的回退，说明作者也没敢依赖它） | §4.4 |
| 9 | `Content-Type` 不可信（实测 `.exe` 给 `application/vnd.microsoft.portable-executable`，官方 issue 却称"所有仓库下载都返回 `application/zip`"） | **别信 Content-Type，信 magic bytes**（前 4 字节 `50 4B 03 04`） | §4.5 |
| 10 | tag 段被服务端校验：错 tag → **404 + `text/html` + 6832 字节错误页**（不是 JSON） | 错误处理必须能容忍"本该是 JSON 却来了 HTML" | §4.5 |
| 11 | 下载**无防盗链**：不带 Referer / 带正确 Referer / 带恶意 Referer 全部成功 | 说明不能靠 Referer 做任何判断 | §4.5 |
| 12 | 单附件 **100 MiB**（GVP 200M）、**每仓库总附件 1 GB**（推荐项目 5G）；且平台以「无相关资质」为由拒绝 apk 等类型下载 | 发布体积与文件类型都要提前卡住 → 只发 `.zip` | §4.8 |
| 13 | 老 URL 格式 `/attach_files/{id}/download`（2020）与新格式 `/releases/download/{tag}/{filename}`（GitHub 风格，现在）**至今都能用** | 平台接口演进是"只加不改"，历史形态会长期共存 | §4.5 |
| 14 | 2020 年就有人在 Gitee 官方 issue 里抱怨：「码云的是数字，这令我程序的检查更新功能很难搞啊」（`git-osc#I1DMXV`，**至今 open**） | 这不是新问题，是这个平台长期存在的形态差异 | §4.2 |

### 21.3 Windows / .NET 的文件锁（我自己写实验推翻了三条流行说法）

**四条可复现规则**（§4.10 实验 A–H）：

| 规则 | 内容 | 为什么重要 |
|---|---|---|
| ① | 运行中的**原生映像**（exe / dll）**能改名、不能删 / 覆盖**；腾位之后**可以在原路径写新文件** | 这是「不重启就换掉自己」的全部基础 → 两阶段替换（先整批改名腾位、再整批落位） |
| ② | 目录内只要有**任何**未关闭的文件句柄（**哪怕带 `FileShare.Delete`**），**目录就不能改名** | 目录比文件严格得多；句柄会 pin 住父目录对象 |
| ③ | **进程 CWD 在目录里 → 目录不能改名** | ★ updater 的 `WorkingDirectory` **绝不能**是安装目录（v1.1 设计里的真实 bug） |
| ④ | 文件能否改名取决于句柄是否允许 delete 共享（`FileShare.Delete`） | 光有 `ReadWrite` 不够 |

**被实验推翻的三条流行说法**：

1. ❌「运行中的 exe 必须先杀掉进程才能更新」→ 其实 **`MoveFileEx` 改名就能成功**，根本不用杀。
2. ❌「被加载的托管程序集会把文件锁住」→ `Assembly.LoadFrom` 是把字节读进内存后**关闭文件句柄**，连删除都能删。（⚠️ 但**不能**把这个结论套到原生 dll 映像上，那走的是另一条路径。）
3. ❌「`FileShare.ReadWrite` 打开的文件不能改名」→ 实测 `Read` / `ReadWrite` / `None` 全部 FAIL，**只有加上 `Delete` 位才 OK**。

**另外两个 PowerShell 的真坑**：

- `Start-Process -Wait` 有两类真实挂起：配 `-Verb RunAs` 会走 ShellExecute **根本不等**；配 `-NoNewWindow` 可能因为流句柄没回收**永久挂住**。→ 用 `-PassThru` + `.WaitForExit()`，或把输出重定向到 `nul`。
- 现代更新器的退出码语义可以借鉴（`/kill` `/backup` `/timeout`；0 成功 / 1 参数 / 2 复制 / 3 MD5 / **5 文件替换失败（被占用）** / 6 其他）。

**杀软是自更新最大的单点风险**：Defender 会**静默**拦截新下载的 exe（"阻止您的软件启动"，可能**没有任何提示**），而且新下载地址 / 新文件会被无条件警报。加数字签名「基本可以避免」。UAC 的推荐策略是「先用非提权方式尝试，失败后再询问用户」。

### 21.5 通往"能自动更新"路上的零碎坑

| # | 坑 | 对策 |
|---|---|---|
| 1 | 本机 exe 名含**全角冒号** U+FF1A（`TFAC剧情箱-轮椅版.exe`） | **不能**用 `cmd.exe /c` 中转启动 updater（引号 + 编码双重地狱）→ 用 `ProcessStartInfo.ArgumentList` 直接起 `powershell.exe`；包名定成 ASCII 前缀从源头规避（O9） |
| 2 | `Start-Transcript` 对**已存在**的文件会退化成**有损 ASCII 编码**（PowerShell issue #13677）→ 中文变问号 | 日志自己写，不用 `Start-Transcript` |
| 3 | WinPS 5.1 脚本不加 BOM 会被当成 ANSI 读 | 脚本必须存成 **UTF-8 with BOM** |
| 4 | `Expand-Archive` 对大量小文件"慢得要死" | 换 `ZipFile.ExtractToDirectory` + 自己扫 zip-slip |
| 5 | zip 里的中文条目名：`Compress-Archive` / Bandizip / `.NET ZipFile` **三种打包器都没写 UTF-8 flag（0x800）** | 但 `.NET ZipFile.ExtractToDirectory` 与 `tar.exe` 解出来名字都**正确** → 不必为此改打包方式 |
| 6 | zip 条目分隔符不统一：`Compress-Archive` / `ZipFile` 写 `\`，**Bandizip 写 `/`** 且会写目录条目 | 比较条目名之前**必须** `Replace('/', '\\')` 归一化 |
| 7 | 本项目**全仓没有 Mutex / 单实例守卫** | 更新前的多实例预检是新功能，不是"复用现成机制" |
| 8 | 校验文档行数时 `Get-Content` 报 1005 行，实际 1365 行 | 用 `ReadAllLines` / ripgrep；别用 `Get-Content` 数行 |
| 9 | **XAML 注释里写 `--`（例如 `--ui-smoke`）→ `XamlCompiler.exe` 静默 exit 1**：零输出、MSBuild 只留一句 `MSB3073`，连是哪个文件都不说，看起来像构建系统自己坏了（2026-10-05 为此花了半小时） | XML 规范本来就不许注释里出现 `--`；写命令行参数名时改成中文说法（「UI 冒烟」），并用例 `界面 XAML 不踩编译器的静默坑` 守着 |
| 10 | 往 `artifacts\` 里放一份界面副本（`.xaml`）→ 界面文件的隐式 glob 是 `**\*.xaml`（只排除 bin/obj）→ 副本被收进编译 → 两个文件抢同一个 `x:Class` → **同样是静默 exit 1** | 界面副本别落在仓库目录里（临时文件放 `%TEMP%`）；同一条用例顺手查 `x:Class` 全仓唯一 |
| 11 | `Get-Content -Raw` 读 UTF-8 中文文件（WinPS 5.1 默认按 ANSI 解码）**再写回去** → 文件被写成乱码（2026-10-05 差点写坏面板 XAML，靠动手前的字节副本救回） | 读写中文文件走 `[System.IO.File]::ReadAllText/WriteAllText` + `[Text.Encoding]::UTF8`；批处理前先留一份 `Copy-Item` 字节副本 |
| 12 | 用 `edit` 之类的工具改覆盖脚本会**丢掉 UTF-8 BOM**：无 BOM 时 `Parser::ParseFile` 按 ANSI 读中文注释 → 报 60 多条假语法错误（`语句块或类型定义中缺少右"}"`），而文件内容其实是好的 | 每次改完 `.ps1` 都补 BOM（`[IO.File]::WriteAllText($p,$t,(New-Object Text.UTF8Encoding($true)))`）并跑一次 `PARSE_ERRORS=0`；用例 `覆盖脚本保持带 BOM 的 UTF-8` 守着 |
| 13 | **覆盖器收尾去起新版本时，包根指向的是 86% 已经删掉的暂存目录** → `Start-Process` 报「找不到文件」→ 一次**成功的**覆盖被改成退出码 6 + 一句「更新失败」，用户会跑去重装（2026-10-05 M4 真机演练实测踩到） | 起新版本前把包内主程序的位置**映射回安装目录**；从这里往后出任何岔子只提醒手动打开，绝不改口说"更新失败"（§9.2 收尾）；用例 `覆盖脚本起的新版本取自安装目录` 守着 |
| 14 | **PS 5.1 跑在 .NET Framework 上，没有 `[IO.Path]::GetRelativePath`**（那是 .NET Core 才有的 API）——在脚本里用它，收尾时抛 `MethodNotFound`，症状与第 13 条一模一样 | 覆盖脚本里的相对路径一律 `Substring($root.Length).TrimStart('\')`（脚本 276/282 行本来就是这套写法）；别把 .NET Core API 当成 Framework 也有 |
| 15 | **用例里写死版本号**（`const string currentVersion = "1.0.1"`）：`<Version>` 一改，`UpdateAvailable` 就变成 `Latest`/`LocalIsNewer`，用例莫名其妙地红，还看不出跟「更新」有什么关系（2026-10-05 M5 写用例时改掉） | 版本号一律 `ApplicationVersionReader.ReadCurrentVersionText()` 现读，「更新的那一版」用一个 `NextPatchVersionAfter(current)` 现算（读不出数字就回落 `999.0.0`，宁可明显地高） |
| 16 | **按文件名里有没有 `.old-` 粗筛回滚文件**：用户自己的 `笔记.old-backup.txt` 也会被算进去，于是「清理完 aged 文件应该为空」这类断言会假红（2026-10-05 M5 用例踩到） | 粗筛只用来枚举候选；真正判定走 `UpdateCleanup.TryStripAgedSuffix`（后缀必须像版本号：数字/字母/`. + - _` 且至少一个数字）；用例里把对照物一起列进期望值，点名「这两份不许动」 |
| 17 | ★★ **进度节流的哨兵值写成了 `TimeSpan.MinValue`**：`elapsed - TimeSpan.MinValue` 必然溢出，抛 `TimeSpan overflowed because the duration is too long`，被下载器的兜底 `catch` 翻译成「下载更新包失败，请稍后重试或到 Gitee 手动下载。」——**每一次带进度条的真实下载都会立刻失败**（M3 就这么上了线；2026-10-06 写分卷用例时第一次传进度收集器才照出来） | 时间差的「还没报过」用 `TimeSpan?` + `null` 判，不要拿 `MinValue` 当哨兵；**新增用例必须覆盖带进度 / 不带进度两条路**（M3 的下载用例都传 `progress=null`，正好把真实界面走的那条路绕开了）；顺手加断言「进度百分比只增不减」 |
| 18 | **分卷的两道校验不能只留一道**：逐卷 SHA-256 能发现「哪一卷坏了」，但发现不了「卷的顺序错了 / 边界错了」——每卷都完好、拼起来却是另一个文件 | 拼完对**整个文件**再算一次 SHA-256 并与 `assets[].sha256`（整包语义）比；任一卷失败即整次失败，**不许留下拼了一半的 `.download`**（它会被下次启动当缓存复用 → 覆盖出半个程序） |
| 19 | ★★ **"最低支持版本"这种自动推导的闸门本身就是坑**：先做成"只透出不拦"（等于没写），改成"真拦"之后又两次把整代客户端关在门外 —— v2.0.3 的清单被算成从未发布的 2.0.2，v2.0.4 被算成 2.0.3，2.0.0/2.0.1 全部只能手动下载（2026-10-06 实测） | **2026-10-06 定案：整个机制删除**（清单字段 + 发布脚本 + 客户端判定）。默认值必须"什么都不拦"；旧版兼容靠新版本自己做到。凡是"自动推出来的闸门"都要先问：算错了会不会把整条升级链关死？ |

### 21.7 方法论：写文章时这一节比坑本身更值钱

1. **官方文档 ≠ 事实。** Gitee 官方 swagger 把自己的 `prerelease` 类型写错；依赖它的代码会把正式版全部过滤掉。**凡是要写进 `if` 判断的字段，先亲手打一发看原始响应。**
2. **"大家都这么说"要亲手验。** 关于文件锁的三条流行说法（必须杀进程、托管程序集锁文件、`FileShare.ReadWrite` 就够）**全被本机实验推翻** —— 代价是半小时写实验，收益是整条设计路线从"先自杀再更新"变成"原地替换"。
3. **别信 `Content-Type`，信 magic bytes。**
4. **同一个状态码可能有多种含义。** 403 既可能是限流、也可能是无权限 → 必须结合 body（`Rate Limit Exceeded`）分类，分类错了就是把"换个 token 能解决"当成"等 20 分钟"。
5. **退避时间要用秒表量出来，不能猜。** 实测 t+240s 仍 403、20 分钟后仍 403 → 才知道必须客户端自己记账。
6. **先找同项目的兄弟实现。** 两个兄弟项目踩过的坑（versionCode、清单站点锁死）直接省掉了本设计最贵的两类事故 —— **它们已经付过学费了**。
7. **把「没有退路」写进风险表。** 只保留一个更新源 = 没有第二源（R11）；这类结构性风险不能靠代码修，只能靠**知道它存在**来管理。

  - 附件列表 `GET …/releases/{id}/attach_files?per_page=100`
  - 删附件 `DELETE …/attach_files/{id}`
  - 传附件 `POST …/releases/{id}/attach_files`（multipart，`access_token` + `file`）
- **上传必须用 `curl.exe --form`**（PowerShell 的 `Invoke-RestMethod` 传 multipart 在这类接口上不可靠）；超过 100MiB 直接放弃上传并提示用 Bandizip 最高压缩重打。
- 顺序建议：建 Release → 传三个附件 → 复查附件名齐全，缺一即报错。
- `prerelease` 由版本号里有没有 `-` 决定（`1.0.1-Beta` → true）；**通道判定完全依赖它，别写错**（注意 §4.7，别用 `!prerelease` 的写法）。
- ★ **每仓库附件总量 1GB** → 发布脚本要有「清理旧 Release 附件」的动作（比如只保留最近 3 个带附件的 Release，更老的删附件但保留 Release 记录）。

```powershell
# Release 列表（★ 必须带 per_page；看 X-RateLimit-Remaining 判断剩余配额）
```
