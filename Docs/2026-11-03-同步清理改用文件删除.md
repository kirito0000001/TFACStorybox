# 同步的「清理多余素材」改成删文件（2026-11-03）

> 起因：2026-11-03 12:25 的一次同步，编辑器在删除阶段崩溃，同步被判失败。
> 结论：不是工具箱外部关掉了编辑器，是 `EditorAssetLibrary.delete_asset` 在**引擎内部**崩的。

## 2. 为什么手动删不崩、脚本删崩（引擎源码）

| 路径 | 实现 | 会不会全库扫描 |
|---|---|---|
| 内容浏览器手动删 | `ObjectTools::DeleteItems` → `FAssetDeleteModel`，**先算引用**；没引用走 `DeleteObjectsUnchecked` → `DeleteSingleObject(bPerformReferenceCheck=False)`（`ObjectTools.cpp:3422`） | **不会** |
| `EditorAssetLibrary.delete_asset` | `UEditorAssetSubsystem::DeleteAsset` **无条件** `ObjectTools::ForceDeleteObjects`（`EditorAssetSubsystem.cpp:793-806`）→ `ForceReplaceReferences(nullptr, …)` 在 `bLimitSearchToPassedObjects=false` 时**遍历 `FThreadSafeObjectIterator` 全部对象**并逐个 `Serialize`（`ObjectTools.cpp:1345-1370`；`FindReferencersArchive.cpp:57`） | **会** |

所以：**同一个 API 在隔壁工程不崩，是因为那边内存里没有那种坏对象**；本项目里有一个带坏 delegate 的 `UFunction`（占位符函数），全库扫描序列化到它就 AV。

> 官方 Python API 文档也写着 `delete_asset` 是 "This is a Force Delete"，且没有暴露轻删路径。

## 3. 改动：顺序 + 删除方式

### 3.1 顺序（用户定）

```
导入素材 → 写变量/表格/立绘 → 保存 → 记录资产类型 → **才删文件** → 注册表重扫 → 复扫验证 → 写结果
```

- 原来那段「先删、再 `save_directory`」被删掉：**save 不删文件，只会把脏包写下去**；
  而且顺序反了会导致「刚删掉、又被保存写回来」。
- 现在删除之后到写结果之间**没有任何保存动作**（`save_directory` 只剩导入阶段的 719 行那一次）。

### 3.2 删除方式

`delete_asset_if_exists` → **`purge_extra_asset`**：

1. `find_package_referencers_for_asset(path, False)` 查引用（只读注册表，不触发全库序列化）；
2. **有引用就跳过** —— 只删文件不会像 ForceDelete 那样把引用置空，硬删会把别人弄坏；
3. 没有引用就 `os.remove` 磁盘上的 `.uasset`；
4. 调用方以**磁盘**复核（`asset_file_exists`），不看任何返回值；
5. 全部删完对涉及的目录做一次 `scan_paths_synchronous`，让 `does_asset_exist` 跟上磁盘。

返回值改成字符串 `"deleted" / "skipped" / "absent" / "failed"`：
**只有 failed 算这次清理没做到**；skipped（有引用）只记 warning，且**不参与复扫判定** ——
否则每次同步都会因为一条「还被引用着」而整次判失败。

## 4. 已知代价

- **内存里那份对象还在**（没走 ForceDelete 的卸载）。它已从注册表移除、也没人引用，下次 GC 或重启编辑器就没了。对「多余素材」这种本就无人引用的东西，实际影响为零。
- **不再有「删除动作」这层语义**：文件删了就是删了，没有引擎侧的引用置空。所以第 2 步的引用检查是必须的，不是可选的保险。
- 删除后如果编辑器又保存了几个脏包，理论上可能把某个文件写回来 —— 现在删除放在所有保存之后，且这些多余的包本来没被改过，不会脏。
